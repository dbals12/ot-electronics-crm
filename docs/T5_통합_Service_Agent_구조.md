# T5 고도화 시스템 구조 상세

> 이 문서는 T5 고도화 기능 전체(가상 IoT·포털·Agent·Hall 대시보드·Slack·FSM)를 **본인이 완전히 이해하고, 팀원에게 설명할 수 있는 수준으로** 정리한 단일 기준 문서다. 여러 대화로 흩어졌던 결정을 한 곳에 모았다. 여기 없는 내용은 아직 결정 안 된 것으로 본다.

---

## 0. 결론부터 — 지금까지 대화로 걸러진 최종 원칙

1. **화면(카드·배지·필드)으로 보이는 정보는 Agent가 다시 말로 설명하지 않는다.**
2. **버튼 클릭 한 번으로 끝나는 정형 동작은 Agent Topic으로 안 감싼다.**
3. **Agent Topic은 "정형 화면·버튼으로 안 끝나는 열린 질문/자유 텍스트"에만 만든다.**
4. **이미 있는 기존 화면·필드·Flow는 다시 만들지 않고 재사용한다** — Agent가 새 데이터 경로를 만들면 안 되고, 기존 필드에 착지해야 한다.
5. 이 네 원칙을 통과한 요소만 최종 설계에 남는다.

## 1. 전체 사용자 여정 (페르소나 × 단계 × 화면 × 방식)

|---|---|---|---|---|---|
| ① 이상 감지 전조 | 유신 | 고객 포털 **자산 상세 화면**(기존 화면에 게이지·이미지 추가) | 상태배지 · 게이지 · 이미지 · 설치일 · 보증 · 최근/다음 점검 · 미조치건수 · 점검이력 | 그냥 화면(Pull, 새로고침 기준) | T5-07 |
| ② 접수 — 주 경로 | 유신 | "Agent 상담" 버튼 → 채팅(포털 전면에 노출) | 대화로 증상 파악 → 기존 폼과 같은 필드에 매핑 → 그 자리에서 Case 생성 | **Agent Topic** `증상 상담` (시나리오상 기본 접수 동선) | T5-08, T5-11 |

## 2. 시스템 구조 (계층으로 보면)

```
┌─────────────────────────────────────────────────────────────┐
│ Surface (사람이 보는 화면)                                      │
│  · 고객 포털 자산 상세(T5-07 통합)  · 장애 신고 폼(기존)          │
│  · Agent 채팅(T5-11)  · Service Console + Case 버튼 2개         │
│    (출동 브리핑·Slack 인계)                                      │
│  · Slack 채널  · Field Service Mobile  · Hall 대시보드(T5-09)   │
├─────────────────────────────────────────────────────────────┤
│ Agent (열린 대화만 담당, 최소한으로 유지 — 결과적으로 유신 전용)     │
│  · 고객용 Topic: 증상 상담 (T5-08) — 폼과 동등한 대안 입구         │
│  · 서정비용 Topic: **없음**(2026-08-28, T5-12 폐기)               │
│  ("내 장비 상태 확인"·"출동 브리핑"·"Case 검토 지원"·"Slack 인계    │
│   요청"·"유사사례 조회"까지 전부 여기서 폐기됨 — 화면/버튼/Flow     │
│   확장으로 대체됐거나 흡수됨. 서정비는 Agent 채팅을 아예 안 쓴다)     │
├─────────────────────────────────────────────────────────────┤
│ Flow / Action (자동화, 대부분 기존 자산 재사용)                    │
│  · OTCaseIntakeController.createCase (기존, Agent도 재사용)      │
│  · Case_Assign_Entitlement_By_Impact (기존, T3/T4 소유)         │
│  · Case_Dispatch_Briefing_Generate (T4 소유, **입력 1개 확장    │
│    허용됨** — 유사사례 요약을 Prompt Template 입력에 추가, T5-20)  │
│  · WOLI_Trend_Flag_Evaluate (T4 소유, 안 건드림)                 │
│  · T5 IoT Reading Subscribe (T5-06, 이미 구현) / Data Cloud     │
│    Triggered Flow (T5-19, Production 프로비저닝 진행 중)         │
│  · Trend/Case Slack Alert (T5-10, 개정: 브리핑 본문 포함)         │
│  · WO Slack 알림 (T5-14)                                        │
│  · 유사사례 검토 Flow/Apex (신규, T5-20)                          │
├─────────────────────────────────────────────────────────────┤
│ Data (전부 기존 표준/커스텀 객체 재사용, 신규 필드 최소화)           │
│  · Asset · WorkOrder · WorkOrderLineItem(Trend_Flag__c 등)      │
│  · Case(Symptom_Category__c·Impact_Level__c·                    │
│    Reported_Symptom__c — 전부 기존 필드) +                        │
│    Similar_Cases_Summary__c(신규, T5-20)                         │
│  · Technical Baseline · Problem                                 │
└─────────────────────────────────────────────────────────────┘
```

**읽는 법**: 위로 갈수록 "사람이 직접 보는 것", 아래로 갈수록 "실제로 돌아가는 로직"이다. Agent 층이 유독 얇은 이유는 0장의 원칙 때문 — 대부분의 일은 Surface 층(버튼·화면)과 Flow 층이 이미 처리하고, Agent는 그 둘로 못 담는 딱 두 자리만 채운다.

### 3-2. 별도 축 — 가상 IoT/Data Cloud → Trend → Alert (포털·대시보드에 배경으로 반영)

```
가상 IoT 시뮬레이터 ──┬── Platform Event 직행 (T5-06, 완료)
(또는 향후 실제 BMS) │
                     └── Data Cloud 경유 (T5-19, Production 프로비저닝 중)
                              │  둘 다 결국
                              ▼

                              │
                    Trend_Flag__c 갱신(정상/주의/이상)
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
              포털 자산      Hall      Trend/Case
              상세 배지     대시보드   Slack Alert
              (T5-07)      (T5-09)    (T5-10, Critical만)
```

**두 축이 만나는 지점**: `WorkOrderLineItem.Trend_Flag__c` 하나다. 3-1(사람이 접수·처리하는 흐름)과 3-2(장비가 스스로 신호를 만드는 흐름)는 서로 독립적으로 움직이다가, 포털 카드·Hall 대시보드·Slack Alert 세 곳에서만 서로의 결과를 보여준다.

### 3-3. Trend Critical 전환 시 Case는 누가 만드나 (2026-08-28 결정)

고객이 아직 신고하지 않은 상태에서 `Trend_Flag__c`가 Critical로 바뀌는 경우가 있다 — 이때 Case를 시스템이 자동으로 만들지, 사람이 만들지가 정해져 있지 않았다.

**결정: 알림만 자동, Case 생성은 사람이 한다.** Trend Critical 전환 → 서정비에게 Slack 알림(기존 T5-10)까지만 자동이고, 그 알림을 보고 실제로 Case를 만들지는 서정비가 판단한다. 이유는 이 프로젝트가 발표 시나리오에서도 반복해서 지켜온 원칙과 같다 — "이 알림이 자동으로 출동·접수를 확정하지 않는다." 시스템이 자동으로 Case까지 만들면 이 절제 원칙과 충돌한다.

**따름 조치**: T5-10에 "Trend Critical Case 생성" 같은 Quick Action(Asset 또는 WOLI 위에서, Trend 컨텍스트를 미리 채운 채 New Case 화면으로 이동)을 추가해 서정비의 수동 생성을 쉽게 만든다.

### 3-4. Hall A 대시보드와 Asset 레코드 페이지는 다른 화면이다 (2026-08-28 명확화)

T5-09가 지금까지 "Hall 대시보드" 하나로 뭉뚱그려 있었지만, 실제로는 **집계 화면**과 **개별 화면** 두 개가 필요하다:

| 화면 | 위치 | 담는 내용 | 참고했던 레퍼런스 |
|---|---|---|---|
| Hall A 대시보드 | Service Console **홈 화면** | Hall A 전체(12~16대) 요약 상태, 영향범위, 예방조치 진행률 | Manufacturing Cloud "Connected Asset Dashboard" 참고했으나 **똑같이 만들 필요는 없음** |
| Asset 레코드 페이지 | 표준 **Asset 오브젝트 Record Page**(FlexiPage), Hall 대시보드에서 드릴다운하거나 직접 진입 | 장비 이미지, 생산·설치·운영 이력(마일스톤 형태), 운영 모니터링 차트(게이지) | Manufacturing Cloud "Service Console For Manufacturing" 참고 |

Manufacturing Cloud 전용 컴포넌트(Milestones 등)가 라이선스로 막히면, Technical Baseline·Change Request·Work Order를 시간순으로 늘어놓는 커스텀 타임라인으로 대체한다. **Manufacturing Cloud 라이선스 확인이 다시 우선순위로 올라옴** — `T5_후속작업트래커.md` #9(낮은 우선순위로 미뤄뒀던 것)를 재우선순위화 필요.

### 3-5. 측정 항목을 유량 외로 확장해도 구조는 안 바뀐다

`Measurement_Item_Code__c`가 이미 범용 분류 필드라서(기존 정기점검 데이터도 "유량"·"체결 상태" 등 여러 항목 공존), 가상 IoT가 다른 측정 항목(차압·온도차·인버터전류 등)을 추가로 발행해도 파이프라인 구조(`IoT_Reading__e` → WOLI 생성 → `WOLI_Trend_Flag_Evaluate` → `Trend_Flag__c`)는 그대로다. `Threshold_Min__c`/`Max__c`도 레코드(측정 항목)별로 이미 따로 저장된다. **바뀌는 건 화면에 게이지가 몇 개 늘어나는 정도** — T5-07/T5-09/이 문서 3-4의 "운영 모니터링 차트"가 여러 개로 늘어나는 것뿐, 아키텍처 변경은 없다.

### 3-6. 디지털 트윈 재조사 — 정정 (2026-08-28)

처음에 "서드파티 AppExchange 제품(Waylay 등)일 뿐"이라고 결론 낸 건 **틀렸다.** Salesforce 자신이 "디지털 트윈"을 자기 제품 마케팅 용어로 쓰고 있고, 그 실체는 **하나의 단일 제품이 아니라 다섯 개 기존 제품을 조합한 아키텍처 패턴**이다:

```
MuleSoft(OT/IoT 게이트웨이 연결)
  → Data Cloud/Data 360(Connect·Harmonize·Unify·Analyze·Predict·Act)
  → Einstein/Agentforce(이상 징후 예측)
  → Tableau(자산 성능 실시간 시각화)
  → Field Service(이상 감지 시 기술자 자동 라우팅)
```

**그리고 이건 우리가 T5에서 이미 만들고 있는 것과 구조적으로 동일하다**:

| Salesforce의 "디지털 트윈" 구성요소 | 우리 T5 구현 |
|---|---|

### 7-1b. 1차/2차/3차 응대 구조 — MIAW ≠ 서비스 에이전트 (2026-08-28 명확화)

멘토가 회의록에서 직접 말한 원칙: **"서비스라는 건 1, 2, 3차로 끊어야 한다."** 이걸 명확히 구조화하면 아래와 같고, **MIAW와 서비스 에이전트(Agentforce Bot)는 서로 다른 층**이라는 걸 여기서 짚는다 — MIAW는 대화가 오가는 **채널(파이프)**이고, 서비스 에이전트는 그 위에서 처음 응답하는 **주체**다.

| 티어 | 누가 응대 | 무엇으로 | 화면 |
|---|---|---|---|
| **1차** | Agentforce 서비스 에이전트(Bot) | Knowledge Article 추천 → 고객 혼자 해결 시도 | 고객 포털 MIAW 채팅창 |
| **2차** | 서정비(사람) | **같은 MIAW 대화를 그대로 이어받음** — 새 세션이 아니다 | Salesforce org의 Case/레코드 화면, 이때 **Customer 360 컴포넌트**가 함께 뜸 |
| **3차** | 오도면·강시공 등 전문가 | Case Swarming(Slack) | Slack 채널 |

**핵심 정정**: 이전 버전(7-1 도식)에서 "미해결 시 Omni-Channel로 서정비에게 실시간 인계"라고 썼는데, "인계"라는 단어가 마치 대화가 끊기고 새로 시작되는 것처럼 읽힐 수 있다. 정확히는 **같은 MIAW 대화창이 그대로 이어지고, 사람이 이어받는 순간 Customer 360이 옆에 뜨는 것**이다. 근거(회의록 원문):

> "이 케이스가 들어오면 일단 서비스 담당자가 1차적으로 상담을 하긴 해야 되잖아요 그랬을 때 실시간 채팅이 인베딩이 되면 **실시간 채팅으로 상담을 계속하면 되는 거고**"
> "그래야지 세일즈랑 계약이랑 확인할 수 있지 않아요, 왜냐면 고객 정보가 아무것도 없잖아요 … 상담할 때 이 고객이 어떤 계약을 했는지, 어떤 제품을 쓰는지 … 그래서 여기에서 세일즈 히스토리"

또한 이 순서(먼저 실시간 채팅 요구사항이 나오고, 멘토가 그 해결책으로 MIAW를 소개)도 회의록에 그대로 남아있다: "상담사랑 실시간 상 대화가 이루어지는 시인가요? — 그것까지는 생각을 못 하셨어요, 오급단에 실시간 채팅 기능이 있는지 몰랐어요." → 즉 MIAW는 처음부터 정해진 답이 아니라, **"Agent가 막히면 사람이 실시간으로 이어받아야 한다"는 요구사항에 대한 해결책**으로 나온 것이다.

### 7-2. 단계별 기존 계획 vs 신규 제안

| ⑤ 사후 지식화·세일즈 연계 | Knowledge Article 자동 등록(T5-22), 기존 시나리오의 "Hall B 증설 Opportunity 연결" 서술 | 신규사례 자동감지·등록 제안 배너(`T5-22` 확장) + 내부 Employee Agent Topic2 "증설 제안 초안"(`T5-28`, W9) |

### 7-3. 구현 방식 가이드 (멘토 지침, 확정)

1. **IoT/Data Cloud는 "모델하우스" 방식으로 충분하다** — 실제 IoT 연동이나 Data Cloud 파이프라인을 무리해서 완성하지 말고, **필드값 하드코딩 + 목업 데이터**로 화면상에서 에러 상태·분석 결과가 자연스럽게 동작하면 충분하다고 멘토가 명시적으로 확인함("IoT 값 한 개 기기만 에러난 거잖아요, 하드코딩으로 박아도 된다"). → **T5-19(Data Cloud, Production 프로비저닝으로 막힘)를 억지로 뚫을 필요 없음. T5-06(Platform Event 직행) 경로로 계속 가도 된다는 근거 확정.**
2. **실물 org에 지어야 한다** — 정적 목업 이미지만 보여주면 숙련된 관객(세일즈포스 경력자)이 바로 알아챈다는 경고. Claude Code로 컴포넌트·Agentforce Action을 실제로 빌드해서 샌드박스에 배포하는 지금까지의 방식이 맞는 방향.
3. **Headless 360은 통째로 도입하지 말고, Slack 보조 시나리오로 녹인다** — 영업 담당자가 Slack에서 Agent를 호출해 "홀A 고객의 최근 케이스 이력과 계약 만료일 분석해서 증설 제안 초안 짜줘"라고 요청하는 정도로 한정. 이게 7-1의 "W9 워크플로우"가 실제로 어떤 화면(Slack)에서 트리거되는지에 대한 답이기도 하다.
4. **숫자를 억지로 맞추지 않는다** — 완료조건을 "정확히 이 수치가 나와야 함"으로 잡지 말 것. 페인포인트를 해결했을 때 실제로 얼마나 베네핏이 있는지를 거꾸로 계산하는 방식으로 QA한다(멘토가 팀의 "숫자 맞추기 매몰" 고충에 직접 정정한 지침).

### 7-4. 멘토의 명시적 우선순위 (시간 부족 시 여기부터)

> "실시간 응대 씬에 힘을 줄 것 같다 — C360 보고, C360 화면 하나만 있으면 되고, Swarming 했을 때 Swarming 채널에 Agent도 같이 따라 들어가서 도움을 주는 씬. 그렇게만 돼도 파워풀해질 거 같다."

**최우선 3가지**: MIAW 실시간 채팅 + Customer 360 화면 + Swarming 채널에 Agent 동행. 나머지(IoT 실시간성 심화, 세일즈 연계 W9)는 "한번 더 생각해보라"는 수준의 다음 단계 과제로 남음 — 지금 전부 다 할 필요는 없음.
