# T5 시각화·실시간 구조 정리 (2026-08-29)

> T5-07 Plan B(SVG 게이지) 착수 직전, 목업 이미지들을 놓고 "고객 포털 트렌드 카드 / Asset 레코드 페이지 / Hall A 대시보드" 3개 화면의 시각화 구조와 실시간성 원칙을 다시 논의해서 정리한 문서. **이 논의로 기존 DEC-T5-01("Warning·Critical 모두 고객에게 능동 알림 없음")이 일부 수정됨** — 근거와 함께 남겨둔다.

## 1. 왜 이 논의가 필요했나

T5-07 Plan B(LWC 내 SVG 게이지) 작업을 시작하려다가, "게이지가 어떻게 생겨야 하는가"를 결정하려면 먼저 **3개 화면이 서로 뭐가 다른지**부터 정해야 한다는 게 확인됨. 여기에 더해 사용자가 냉각 산업의 실제 도메인 지식(액체로 연결된 시스템이라 국소 이상이 전체로 전파돼 데이터센터 셧다운까지 갈 수 있음)을 근거로 "Pull 방식·능동 알림 없음" 원칙에 정당한 이의를 제기 — 원칙 자체를 다시 검토하게 됨.

## 2. 시각화 3접점 비교

| | **T5-07 포털 Trend 카드** | **T5-21 Asset 레코드 페이지** | **T5-09 Hall A 대시보드** |
|---|---|---|---|
| **보는 사람** | 유신(고객) | 서정비·오도면·강시공(내부) | 서정비·오도면(내부) |
| **범위** | 자산 1개 | 자산 1개 | Hall A 전체(12~16대) |
| **시각화 형태** | 다이얼 게이지 **N개**(비정상 항목만, 아래 5장 참고) | 다이얼 게이지 **N개**(전체 측정 항목) + 센서 위치 마커 오버레이 | 자산별 미니 상태 인디케이터 그리드 |
| **정보 밀도** | 최소 — "괜찮은지 아닌지" | 최대 — 진단에 필요한 전부 | 요약 — "전체 중 몇 대가 문제인가" |
| **갱신 방식** | **Pull(기본) + Critical만 능동 신호**(3장 참고) | **실시간 가능**(`lightning/empApi`, 4장 참고) | Pull |
| **시나리오 연결** | 고객이 이상을 처음 인지(Scene 1) → Agent 상담(T5-08/23) | ① 출동 브리핑에서 서정비가 AI 판단을 직접 게이지로 재확인 ② Slack에서 오도면·강시공이 현장 대응 전 독립 확인(6장) | Problem/RCA 화면에서 "이 원인이 나머지 11대에도 해당하는가" 확인하러 드릴다운(6장) |

**컴포넌트 재사용 원칙**: 게이지 SVG 컴포넌트는 **하나만 만들고 세 화면에서 다르게 씀** — T5-07/T5-21은 같은 컴포넌트를 여러 번(측정 항목 수만큼) 반복 렌더링, T5-09는 그 컴포넌트의 축소판(라벨·눈금 생략, 색상 점 수준)을 씀. 컴포넌트를 3벌 따로 만들지 않는다.

## 3. 실시간·능동 알림 원칙 개정 — DEC-T5-01 수정

**기존 원칙(DEC-T5-01, 이번에 일부 수정됨)**: "Warning은 조용히, Critical은 서정비에게만 Push, 고객에게 가는 능동 알림은 아예 없음."

**수정 근거(사용자 제기, 2026-08-29)**: 냉각 설비는 액체로 물리적으로 연결된 시스템이라, 국소적 온도·유량 이상이 전체로 전파돼 **데이터센터 전체 셧다운**까지 이어질 수 있다. 이런 안전 관련 리스크에서 "고객이 스스로 새로고침해서 확인하길 기다리는" Pull 방식은 실제 대응 지연을 유발할 수 있다 — 이건 일반적인 "알림 피로 방지" UX 배려와는 다른 급의 문제.

**수정된 원칙**:

| | Warning | Critical |
|---|---|---|
| 서정비(내부) | 알림 없음(기존 유지) | Slack Push(T5-10, 기존 유지) |
| **유신(고객)** | **알림 없음(기존 유지)** — 사소한 변동으로 불안하게 하지 않음 | **능동 신호로 변경**(신규) — 안전 문제라 고객이 알아서 확인하러 오길 기다리면 안 됨 |

**왜 Warning은 그대로 두는가**: 오탐지·미세 변동까지 고객에게 능동으로 보여주면 전문 지식 없는 고객이 정상 노이즈와 진짜 문제를 구분 못 해 불필요한 불안·문의를 유발한다. Critical만 예외를 두는 게 "필요한 만큼만 능동적"이라는 절제 원칙과도 일치한다.

**구현 방식**: 전체 측정값을 실시간 스트리밍하는 게 아니라, **`Trend_Flag__c`가 "이상"으로 전환되는 이벤트만 좁게 구독**(`lightning/empApi`, `IoT_Reading__e` 또는 별도 Critical 전환 이벤트)해서 포털에 배너를 띄우는 정도로 충분함. 실제로 이전 세션 목업(고객 포털 상세 화면)에 이미 "A-07 유량 하락이 감지됐습니다 [상담 시작]" 배너가 있었던 것 — 이게 우연이 아니라 원래 있어야 했던 설계였다는 게 이번에 확인됨.

## 4. T5-21은 실시간 스트리밍 가능 — T5-07과 원칙이 다른 이유

T5-21(내부용)은 진짜 실시간(`lightning/empApi`로 `IoT_Reading__e` Platform Event 직접 구독)이 가능하고, 그렇게 가는 게 맞다. T5-07(고객)은 Critical 예외를 빼면 여전히 Pull이다. 같은 데이터인데 화면마다 갱신 방식이 다른 이유:

- **역할 차이**: 서정비·오도면·강시공은 업무 시간에 콘솔을 켜놓고 지속 감시하는 역할 — 실시간이 실사용 가치가 있음. 고객은 가끔 확인하러 오는 사람 — 상시 스트리밍의 효용이 낮음(Critical 예외 제외)
- **정보 해석 능력 차이**: 내부 인력은 미세 변동의 의미를 판단할 전문성이 있음. 고객에게 초 단위로 흔들리는 원본 수치를 그대로 보여주면 오해를 유발할 수 있음
- **기술·라이선스 차이**: Experience Cloud(Guest/External User)의 Platform Event 구독은 내부 Lightning보다 설정이 까다로움 — 다만 이건 부차적 이유, 위 두 가지가 핵심 근거

**주의 — "750ms" 같은 구체적 숫자를 화면에 박지 말 것**: 목업 이미지 중 "LIVE 750ms SYNC" 배지가 있었는데, 지금 우리 목업 발행기는 정해진 주기로 도는 스케줄러가 아니라 수동/이벤트성 발행이라 이 숫자는 근거가 없다. **개념(실시간 스트리밍)은 유지하되, 화면엔 구체적 ms 수치를 넣지 않거나("실시간" 정도로 표현), 실제로 그 주기로 발행하는 Scheduled Flow를 만들어서 숫자를 진짜로 만들거나** 둘 중 하나로 가야 한다 — 이 프로젝트의 "근거 없는 숫자를 화면에 안 박는다" 원칙과 일관되게.

## 5. T5-07 게이지 항목 수 — "유량" 고정에서 "비정상 항목 전부"로 변경

**기존(수정 전)**: 게이지 1개, 측정 항목은 "유량"으로 고정(설계 초기 예시가 그대로 굳어진 것, 원래 근거 있던 제약 아니었음).

**수정**: **현재 비정상(주의/이상) 상태인 측정 항목 전부**를 게이지로 표시. 유량만 이상이면 1개, 유량+온도가 동시에 이상이면 2개. `Measurement_Item_Code__c`가 이미 범용 필드라 T5-21과 동일한 반복 렌더링 방식으로 구현 가능 — 별도 컴포넌트 불필요(2장 "컴포넌트 재사용 원칙" 참고).

정상인 항목까지 다 보여주지는 않음 — 그건 여전히 T5-21(내부 SCADA 전체 패널)의 역할이고, 고객용은 "지금 문제 되는 것만" 보여주는 게 정보 밀도 원칙과 일치.

## 6. 시나리오 삽입 지점 3곳

목업 흐름(고객 접수 → Agent → 서정비 상담 → 출동 브리핑 → Slack Swarming → FSM)에 T5-21·T5-09를 어디에 끼워넣을지 정리.

### 6-1. 출동 브리핑 화면 → T5-21 (서정비의 1차 검증)

출동 브리핑 화면에 "Asset 레코드에서 실시간 게이지 확인" 링크 추가. 서정비가 AI 브리핑을 그대로 승인하는 대신, 실제 게이지(T5-21)를 한 번 더 열어보고 확정 — "AI가 원인을 확정한 것이 아니다"라는 이 프로젝트의 핵심 메시지를 화면 흐름으로 보여주는 지점.

### 6-2. Slack Swarming → T5-21 (오도면·강시공의 2차 독립 검증)

Slack 메시지(Case 요약)에 Asset 레코드 링크 포함. 오도면·강시공이 데스크탑/모바일에서 링크를 눌러 T5-21(SCADA 패널+게이지)을 직접 확인한 뒤, 그 판단을 Slack 스레드에 텍스트로 올림. 6-1(서정비)과 다른 사람·다른 목적의 검증이라 **중복이 아니라 "AI 제안 → 사람 검증"을 여러 층에서 반복해서 보여주는 효과**.

**기술적 한계**: Service Cloud for Slack의 표준 기능으로 Salesforce 레코드 링크를 붙이면 **요약 카드(필드 몇 개) 미리보기**는 Slack 안에 뜬다. 하지만 우리가 만드는 커스텀 SVG 게이지 화면 자체가 Slack 안에서 그대로 렌더링되지는 않는다(Slack이 Lightning 컴포넌트를 못 그림) — 링크 클릭 시 Salesforce(브라우저/모바일 앱)로 넘어가야 진짜 게이지를 볼 수 있음. "Slack 안에 직접 보이면 좋겠다"는 기대는 요약 카드 수준까지만 맞다고 기대치를 맞춰야 함.

### 6-3. Problem/RCA 화면 → T5-09 (서정비·오도면의 예방 범위 확인)

A-07 하나의 근본원인이 나머지 11대의 예방 조치로 확장되는 지점(Problem/RCA "장면 2의 반대 방향" — 공통 조건 확인)이라, Hall A 대시보드(T5-09, "12대 중 몇 대 예방 확인 완료")로 드릴다운하는 링크를 Problem/RCA 화면에 추가. T5-09의 원래 정의("영향범위·예방조치 진행률")와 정확히 맞아떨어지는 연결.

**⚠️ 조율 필요**: Problem/RCA 화면은 T5 티켓이 아니라 기존(T3/T4) 구축 화면으로 보임 — 여기에 링크를 추가하려면 T5-20 때처럼 해당 트랙에 확인이 필요할 수 있음. 또한 T5-09는 **트랙 B 소관**이라, 이 연결 작업 자체는 트랙 B와 조율해서 진행해야 함(이 문서엔 설계만 남기고, 실행은 트랙 B 백로그에 반영 요청 필요).

## 6-4. 게이지 옆 보조 시각화 2종 추가 (2026-08-29, 업계 조사 대조 후 결정)

외부 조사 자료(데이터센터 냉각 모니터링 업계 표준 시각화)와 우리 시스템을 층별로 대조한 결과, "④ 서비스·운영 의사결정 값"층은 이미 잘 갖춰져 있지만 "24시간 추세"·"전후 비교"가 빠져 있었음이 확인됨. 이 둘은 **큰 추가 없이 지금 있는 실데이터로 바로 만들 수 있어 T5-07/T5-21 게이지 옆에 같이 추가하기로 함.**

- **스파크라인(최근 추세)**: 같은 Asset·측정 항목의 최근 N건 `Measured_Value__c`를 작은 선 그래프로. Controller가 지금 "최신 1건"만 조회하는 걸 "최근 N건"으로 확장하면 됨(실데이터: 오늘 T5-06 시딩분)
- **전후 비교 미니 카드**: **"68→112" 같은 특정 서사 수치가 아니라, 실제 존재하는 `Delta_From_Previous__c`(현재값 vs 직전값)를 일반화해서 사용** — CDU-A-07의 실제 시운전 이력이 org에 없다는 게 이미 확인된 사실(별도 미해결 이슈로 팀 공유 대기 중)이라, 그 특정 수치에 의존하면 빈 카드가 뜸. "최근 vs 직전"으로 범위를 좁혀서 지금 있는 데이터로 동작하게 하고, 나중에 실제 시운전 이력이 시딩되면 필드 재사용으로 자동 반영되게 설계
