# T3 학습 정리본

> 이 문서는 T3 작업을 진행하며 자연스럽게 알게 된 것들을 관점별로 정리합니다. 대화 중 나온 통찰은 별도 요청 없이 계속 추가됩니다.

## 🗺️ 핵심 개념 지도 (헷갈리는 객체들 정리)

Asset·WorkOrder·WorkType·Work_Subtype__c·WorkOrderLineItem·Pricebook2·PricebookEntry가 계속 나와서 헷갈릴 때 참고.

| 개념 | 정체 | 목적 |
|---|---|---|
| Product2 (Product) | 제품 "모델" 자체 (카탈로그) | "ColdFlow CDU-1700"이라는 제품 종류 정의 |
| Asset | 실제 설치된 **장비 1대** | "CDU-A-07"이라는 물리적 기계 한 대 추적 (Product2 참조) |
| WorkOrder | 작업 지시서 1건 | "이 작업을 하겠다"는 일감 단위 |
| WorkType | 작업 "유형" 마스터 레코드 | **일정 계산용**: 예상 소요시간·근무시간·필요 기술 (스케줄링 목적) |
| Work_Subtype__c | WorkOrder의 커스텀 **필드** (객체 아님) | **업무 분류용** 태그, 여러 트랙 공용, 자동화 로직 필터링용 |
| WorkOrderLineItem (WOLI) | WorkOrder 안의 "줄" | 세부 항목 — 의미는 Task마다 다름(도메인 로직 섹션 참고) |
| Pricebook2 (Price Book) | "가격표" 자체 | 제품들의 가격 목록을 묶는 컨테이너 |
| Standard Price Book | Pricebook2의 유일한 기본값 | 가격표가 하나뿐이라 이것만 사용 |
| PricebookEntry | Product2 + Pricebook2의 조합 레코드 | WOLI가 제품을 참조할 때 반드시 거쳐야 하는 플랫폼상 다리 (비즈니스 의미 없음) |

**관계도** (위→아래로 참조):
```
Product2 (ColdFlow CDU-1700)
   └─ Asset (CDU-A-07)
        └─ WorkOrder (CDU-A-07 시운전 작업)
             ├─ WorkTypeId → WorkType(시운전)        ← 일정 계산용
             ├─ Work_Subtype__c = "시운전"           ← 분류용 태그
             └─ WorkOrderLineItem × N
                   └─ PricebookEntryId → PricebookEntry
                         ├─ Product2Id → Product2
                         └─ Pricebook2Id → Standard Price Book
```

## 🧭 비즈니스 프로세스 관점

세일즈포스 자체보다 "왜 이렇게 일이 흘러가는가"에 대한 이해.

- Salesforce는 화면 클릭으로 즉시 반영되는 시스템이라, 여러 사람이 같은 org에서 동시에 손대면 서로 덮어씀 → 그래서 GitHub 경유 + 개인 Sandbox 분리 구조를 쓴다.
- 트랙을 나누는 기준은 "누가 어떤 업무(UC)를 맡는가"가 아니라 **"누가 어떤 객체를 소유하는가"** — 하나의 업무 흐름(UC)이 여러 객체를 가로질러 지나가기 때문에, UC 단위로 나누면 여러 사람이 같은 객체를 건드리게 된다.
- **Contract가 `Activated`로 바뀌는 시점 = 법적 구속력이 생기는 확정 시점.** Technical Baseline(기술 기준선)은 이 확정 시점의 스냅샷이어야 하며, 아직 협상 중일 수 있는 Customer Commitment·Quote 자체를 기준으로 만들면 안 된다.
- 여러 트랙이 같은 코드값(`Measurement_Item_Code__c`: 유량·수온·차압·전류·누기·체결토크)을 시계열로 연결하려면 철자가 100% 일치해야 한다 — 그래서 팀이 사전에 문서로 값을 못박아둔다.
- **코드(Apex/LWC)를 언제 도입할지는 "미리 계획"이 아니라 "트리거 조건"으로 관리한다.** 지금 백로그의 모든 Task가 Flow·Validation Rule·Approval Process 같은 선언형으로 커버되고, 진짜 코드가 필요한 이유(복잡한 대량 처리, 외부 시스템 동기 콜아웃, 표준 화면으로 불가능한 UI)가 하나도 없다면 커스터마이징 단계를 백로그에 미리 넣지 않는다(Salesforce의 "Clicks before Code" 원칙). 대신 "이 조건이 생기면 그때 논의한다"는 트리거만 정해둔다 — 이 프로젝트는 "실제 ERP/PLM/BMS 외부 연동이 승인되는 순간"이 그 트리거. Flow 일부를 나중에 Apex로 바꾸는 건 부분 교체로 가능해서, 미리 설계 안 해둬도 되돌릴 게 없다.
- **비즈니스적으로 의미가 없고 선택지가 하나뿐인 값(예: Price Book)은 자동화하고, 실제로 의미가 갈리는 값만 사람이 고르게 한다.** 나중에 선택지가 여러 개로 늘어나도, 자동화 로직을 한 곳(Get Records 하나)에 모아뒀다면 그 지점만 고치면 되고 나머지 구조는 안 건드려도 된다 — 처음부터 "혹시 몰라서" 사람이 고르게 만들어둘 필요는 없다(YAGNI).
- **필드가 어느 객체에 속하는지(객체 소유권)와, 그 값의 원본이 어디서 오는지(데이터 원천)는 별개다.** 예: `Technical_Baseline__c` 객체 자체는 T3 소유지만, 승계해올 값의 원본(`Customer_Commitment__c.Delivery_Date__c` 등)은 T1 소유. 그래서 T3가 Flow는 먼저 만들어도, 실제 값 매핑은 T1 작업이 끝나야 완성된다.
- **"보증 기산일"은 "보증이 시작되는 날짜"를 못박는 값이고, 왜 별도로 "고정·불변" 관리가 필요한지가 T3-21의 핵심**(T3-21, 보증 기산 + 보증·서비스계약 자동 생성). 인수는 **조건부인수**(설치는 끝났고 사소한 잔여 작업은 남아있어도 고객이 일단 받아들이는 시점) → **최종인수**(그 잔여 작업까지 다 끝난 시점) 2단계로 진행되는데, 만약 "보증 시작일 = 최종인수일"로 잡으면 잔여 작업이 늦어질수록 보증 시작일도 자동으로 밀리면서 보증 기간이 실질적으로 늘어나버린다(회사가 자기 지연 때문에 보증 부담을 스스로 키우는 셈). 그래서 원칙은 **"보증 기산일은 조건부인수 시점에 딱 한 번 기록되면, 이후 최종인수로 레코드가 다시 저장돼도 절대 재기록되지 않는다"** — 이 불변성 자체가 완료조건의 핵심이라, 구현도 "값을 계산하는 로직"보다 "이미 값이 있으면 아무것도 안 하고 종료하는 가드"가 더 중요하다(구현 방식은 아래 개발자 관점 참고).
- **인수 확정 하나가 표준 객체 두 개(Entitlement·Service Contract)로 자동 번역된다**(T3-21). Entitlement는 "이 자산이 언제부터 언제까지 보증/서비스 대상인가"를 나타내는 표준 Salesforce 객체이고, Service Contract는 그 보증을 감싸는 계약 레코드다. 이 두 레코드를 인수 시점에 자동으로 만들어두면, 나중에 고객이 고장 신고(Case)를 넣었을 때 "이게 무상보증 대상인지"를 시스템이 Entitlement 날짜로 즉시 판정할 수 있다(T4 트랙 O2가 이 값을 쓰는 소비자) — 안 만들어두면 Case마다 사람이 "이 장비 보증 언제 끝나지?"를 수동으로 계산해야 한다.

## 🔧 도메인 로직 (업무 자체를 이해하기 위한 배경지식)

Salesforce 기능이 아니라, "이 업무가 실제로 뭘 의미하는지" 몰라서 헷갈렸던 것들.

- **"Line Item(줄)"이 가리키는 대상은 Task마다 다르다** — Work Order 1건이 "여러 대의 장비"를 다루는 작업이면 Line Item 한 줄 = "장비 한 대"(T3-03 설치: 12줄 = CDU 12대). 반대로 Work Order 1건이 "장비 한 대"에 대한 작업이면 Line Item 한 줄 = "검사/작업 항목 하나"(T3-04 시운전: 6줄 = 유량·수온·차압·전류·누기·체결토크 6개 검사 항목, 장비는 `AssetId` 하나로 고정). **Work Order가 무엇을 "묶는 단위"인지부터 파악해야 Line Item의 의미를 알 수 있다.**
- **Punch(펀치)란 "시운전 중 발견됐지만 아직 안 고쳐진 문제 목록"**이다(건설·설비 업계 용어). 측정값이 기준 범위를 벗어나 불합격이 나오거나, 눈으로 발견한 다른 결함(라벨 오기 등)이 Punch가 된다. 심각도(Critical/Major/Minor)로 분류하고, 상태(Open→조치중→조치완료→검증완료)로 진행을 추적하며, **본인이 "고쳤다"는 걸로 끝나지 않고 제3자(검증자)가 확인해야 완전히 닫힌다** — 이게 나중에 "Critical Punch가 하나라도 남아있으면 최종인수 자체를 막는다"(T3-09)는 규칙의 전제가 된다.
- **"심각도"와 "처리 상태"는 절대 하나로 합치면 안 된다** (T3-20 검증 중 실제로 마주친 판단). Severity__c(심각도)는 **그 결함이 원래 얼마나 심각했는가를 기록하는 영구 분류**고, Punch_Status__c(처리 상태)는 **지금 처리가 어디까지 됐는가를 기록하는 진행 상태**다. 급할 때 "검증완료되면 심각도를 지워서 카운트에서 빼자"는 유혹이 있는데, 이러면 나중에 "이 장비에 Critical 결함이 총 몇 번 있었나?" 같은 이력 조회가 통째로 무너진다(해결된 건 전부 심각도가 지워져 있으니). **집계·차단 로직이 필드 하나를 잘못 봐서 생긴 버그는, 사람이 데이터를 조작해서 우회하지 말고 로직을 고쳐야 한다** — 데이터의 의미를 지키는 쪽이 항상 우선이다.
- **설치는 "여러 대를 한 번에" 처리하지만, 시운전은 "한 대씩 개별로" 진행한다** — 실제 현장에서 장비를 설치할 땐 여러 대를 한꺼번에 반입·설치하는 반면, 시운전(정상 작동 확인)은 장비 하나하나를 따로 검증해야 하기 때문에 이런 구조 차이가 생긴다.
- **"미조치 Punch 상시 집계 + 기한 초과 자동 노출"(T3-19)이 실제로 막는 사고**: Punch는 현장에 수십 개씩 쌓일 수 있어서, 사람이 매번 목록을 열어 "이거 기한 지났나?"를 확인하는 걸 깜빡할 수 있다. 특히 Critical(누기 등 안전·품질 직결) 항목이 방치되면 위험하다. 그래서 ① WorkOrder·Asset 화면에 "미조치 개수"를 필드로 상시 노출하고, ② 매일 새벽 시스템이 스스로 기한 초과 Punch를 스캔해서, ③ 담당자(WorkOrder Owner)에게 자동으로 Task를 만들어 찔러준다 — 사람이 매일 확인 안 해도 방치된 문제가 스스로 담당자에게 알림으로 올라오는 구조.

## 🗓️ Field Service 도메인 (Service Appointment·Territory·Resource)

Field Service 스케줄링 구조를 몰라서 헷갈렸던 것들.

- **Service Territory Member는 Service Resource → Territory 연결과 별개의 레코드다.** Resource를 Territory에 할당해도 Territory Member 레코드를 따로 만들지 않으면 스케줄링 엔진이 그 Resource를 인식 못 함 — "no service territory member defined" 에러로 나타남. Member 레코드엔 유효기간(Start Date)이 있어서, SA 예정 시작 시각보다 늦으면 똑같이 에러남.
  - 해결: Service Territories → 해당 Territory → Service Territory Members → New → Resource 지정 + Start Date를 SA 시작보다 앞으로
- **FlexiPage(Lightning Record Page)는 deploy 후 반드시 Activation을 별도로 해야 한다.** deploy만 하면 org에 파일은 올라가지만 화면에는 기본 레이아웃이 뜸. Lightning App Builder → Activation → Assign as Org Default(또는 App/Profile 지정) 해야 커스텀 화면이 적용됨.
- **FlexiPage Activation 시 메타데이터가 바뀐다** — 탭 컴포넌트에 `label` 속성 등이 추가됨. Activation 완료 후 반드시 `retrieve_metadata` → `git diff` 확인 → 변경분 커밋까지 해야 org 상태와 git이 일치함.
- **Service Appointment Status가 기술자 배정 시 자동으로 "Scheduled"로 전환된다** — Assigned Resource를 저장하는 순간 FSL 패키지가 Status를 바꿔줌. 별도 Flow 불필요.

## 🛠️ 어드민(Salesforce 설정) 관점

Setup 화면 조작하면서 겪은 함정들.

- **Field Name에 `__c`를 직접 입력하면 안 됨** — 저장 시 자동으로 붙기 때문에 직접 넣으면 `Xxx__c__c`가 되어 에러남. Field Name 칸엔 접미사 없이 입력.
- **메타데이터 배포(deploy)로 만들어진 필드/Tab은, Setup 화면 마법사로 만든 것과 달리 프로필의 FLS(Field-Level Security)·Tab Visibility가 자동으로 안 붙을 수 있다.** 다른 트랙이 만든 게 안 보이면(리소스 목록, App Launcher 등) 이것부터 의심.
  - 필드: Object Manager → 필드 클릭 → Set Field-Level Security
  - Tab: Setup → Profiles → 해당 프로필 → Object Settings → Tab Settings
- **FLS(볼 권한 있음)와 Page Layout(화면에 배치됨)은 완전히 별개 개념.** 필드가 존재하고 권한도 있어도 Page Layout에 안 올라가 있으면 입력 화면엔 안 보인다.
- `git pull`은 로컬 파일만 갱신한다 — **Sandbox org 자체에는 별도로 `SFDX: Deploy Source to Org`(또는 `sf project deploy start`)를 해야 반영된다.**
- **Data Import Wizard는 Asset을 지원하지 않는다** (Account/Contact/Lead 등만 지원) — Data Loader나 CLI 필요.
- Data Loader에서 관계 필드(Lookup)를 "이름"으로 자동 매칭하는 기능은, 대상 필드가 Unique/External ID로 지정돼 있지 않으면 동작하지 않는다 — 표준 Name 필드로는 안 되고, 실제 18자리 Record ID를 직접 넣어야 한다.
- **untracked 잔여 파일 정리할 때 폴더째 지우면 위험하다.** 표준 객체 폴더(`WorkOrder/` 등)엔 우리가 실제로 만들어 이미 git에 커밋·merge된 커스텀 필드와, retrieve 때 같이 딸려온 무관한 표준 필드가 섞여 있을 수 있다. 폴더 전체를 지우면 tracked 파일까지 같이 삭제(`D`로 표시)돼버린다 — 다행히 커밋 전이면 `git restore <경로>`로 tracked 파일만 복구되고 untracked 잔여물은 그대로 사라져서 결과적으로 정리가 되지만, 커밋 후에 이런 실수를 하면 되돌리기 번거롭다. `git status`로 뭐가 modified/untracked인지 먼저 확인하고 지우는 습관이 필요.
- CSV에 한글이 있으면 Windows Excel이 저장할 때 기본적으로 UTF-8이 아니라 시스템 코드페이지(CP949)로 저장해서 깨진다 — UTF-8(BOM 포함)으로 변환해야 한다.
- **새 필드를 만들면 FlexiPage 확인이 사실상 필수 체크리스트다.** T3-09(인수 유형 3필드)·T3-18(`Has_Evidence__c`)·T3-19(`Open_Punch_Count__c`)·T3-20(Asset 6필드 자체는 Asset에 FlexiPage가 없어 괜찮았지만 그 검증에 쓴 WorkOrder 쪽 인수 필드들) — **네 번 연속으로 "필드는 배포됐고 FLS도 있는데 화면에 안 보인다"가 재현됐다.** 원인은 매번 같다: WorkOrder가 커스텀 FlexiPage(`WorkOrder_Record_Page`)를 쓰는데, 새 필드를 그 FlexiPage에 추가하는 걸 깜빡함. **Page Layout에 필드를 추가하는 것과 FlexiPage에 추가하는 것은 완전히 다른 화면 시스템**이고, FlexiPage가 있는 객체는 Page Layout 편집이 화면에 아무 영향을 안 준다. → 앞으로 새 필드를 만들 때마다 "이 객체에 커스텀 FlexiPage가 있는가"부터 확인하고, 있으면 그 자리에서 같이 추가하는 습관이 필요하다(나중에 따로 고치면 매번 같은 디버깅을 반복하게 된다).
- **Roll-Up Summary 필터는 "특정 값 제외"는 되지만 "공란 제외"는 안 된다.** `Punch_Status__c notEqual 조치완료`처럼 구체적인 값을 걸러내는 필터는 정상 동작하지만, `Punch_Status__c notEqual ""`(공란 아님)처럼 빈 값을 걸러내려는 필터는 실제로 적용이 안 된다(재배포해도 그대로). 반대로 **같은 걸러내기를 Flow의 `Get Records`로 하면 `IsNull` 연산자가 정상 동작**한다. 그래서 "공란인지 아닌지"를 걸러야 하는 집계는 Roll-Up Summary가 아니라 Flow로 만드는 게 안전하다 — 다만 "이 값이 아닌 것"(특정 값 제외)만 필요하면 Roll-Up Summary로도 충분하다(`Critical_Punch_Count__c`에 `Punch_Status__c notEqual 검증완료` 필터를 추가해서 실제로 고친 사례).
- **다른 사람이 "이 버그 고쳤다"고 해도, 내 PR이 겪은 CI 실패의 원인이 그거라고 그냥 믿지 않는다.** 팀원이 공유 Permission Set의 `<readable>` 중복 버그를 고치고 "#62·#64 CI 실패도 이것 때문일 수 있다"고 했는데, 실제로 두 브랜치를 직접 열어보니 **그 중복이 애초에 없었다**(이미 각자 브랜치에서 따로 고쳐뒀던 것) — 진짜 원인은 완전히 다른 문제(T0INT 미배포)였다. "그럴듯한 설명"과 "내 상황에 실제로 해당하는 원인"은 다르다 — 항상 내 브랜치의 실제 상태를 직접 확인한 뒤에 "이게 원인이 맞다/아니다"를 판단해야 한다.
- **CI(sfdx-git-delta)는 XML 메타데이터를 "파일 단위"로 변경 판정한다, 줄 단위가 아니다.** Permission Set처럼 필드 권한이 수백 줄 들어간 파일을 조금이라도 건드리면(필드 하나 추가만 해도), **그 파일 전체가 이번 변경분으로 취급돼 배포 검증 대상에 통째로 들어간다** — 내가 손도 안 댄 다른 줄(예: 다른 트랙이 최근에 넣은 필드 참조)까지 같이 검증받는다는 뜻. 그 참조가 검증 대상 org에 아직 없으면, 나는 아무것도 안 건드렸는데도 내 PR이 막힌다. **공유 파일(Permission Set·Profile 등)을 건드리는 PR은, 그 파일의 다른 부분이 대상 org에 이미 반영돼 있는지까지 신경 써야 한다.**

## 💻 개발자(Flow/데이터 로직) 관점

자동화 설계하면서 얻은 패턴.

- Record-Triggered Flow에서 "생성 시" vs "업데이트 시"는 **실제 업무상 그 이벤트가 언제 일어나는지**로 결정해야 한다. 예: Contract는 기본적으로 Draft로 "생성"되고, 나중에 누군가 Status를 Activated로 "수정"하므로, 체결 시점을 잡으려면 트리거는 Update여야 한다.
- **"Only when a record is updated to meet the condition requirements"** 옵션이 상태 전이(예: Draft→Activated로 "바뀌는 순간") 감지의 핵심 — 이게 없으면 조건을 계속 만족하는 레코드가 다른 이유로 수정될 때마다 Flow가 매번 재실행된다.
- Fast Field Update(Before Save) vs Actions and Related Records(After Save)의 선택 기준: **같은 레코드의 필드만 바꾸는가, 아니면 다른 레코드를 만들거나 고치는가.**
- Get Records로 조회한 결과는 Flow 화면의 `ELEMENTS` 트리가 아니라 **`RESOURCES > Record (Single) Variables`** 에서 필드를 참조할 수 있다.
- 중복 생성 방지 패턴: Get Records(조건에 맞는 기존 레코드 조회) + Decision(`Is Null` 체크)을 조합해서, 이미 있으면 생성 안 하고 없으면 생성하는 분기를 만든다.
- **필드에 리터럴 값을 고정해도 되는지 판단하는 기준**: "이 값이 레코드마다 달라야 하는 식별자인가"(예: 이름) vs "이 Flow가 하는 일 자체가 그 값을 정의하는가"(예: "Rev.A 생성 전용 Flow"의 버전값). 전자는 반드시 동적으로(Formula·참조), 후자는 고정값으로 두는 게 맞다 — 무조건 다 동적으로 만들 필요는 없다.
- Flow에서 리터럴 값(고정 텍스트, 피클리스트 값)을 넣을 땐 **리소스 선택 도구를 쓰지 않고 그냥 평문으로 타이핑**한다. `{!}` 문법을 손으로 치면 안 됨(문자열로 인식 안 되고 에러남) — 그건 항상 선택 도구로만 채워지는 형식.
- **Required(필수) 필드는, 그 값을 실제로 채워줄 자동화(또는 소스 데이터)가 아직 없는 상태에서는 레코드 생성 자체를 막는다.** 값 매핑이 아직 미완성이면 임시로 Required를 풀어두고, 나중에 실제 매핑이 완성되면 다시 검토하는 식으로 단계적으로 접근하는 게 실용적이다.

- **`doesRequireRecordChangedToMeetCriteria` + OR 조건 조합의 함정**: 트리거 필터에 `1 OR 2` 같이 여러 값을 걸면, 레코드가 이미 조건을 만족하는 상태(예: `등록`)에서 다른 값(예: `변경요청전환`)으로 바뀌어도 Salesforce는 "조건 변화 없음(계속 TRUE)"으로 판단해 Flow를 실행하지 않는다. 이 옵션은 필터가 FALSE→TRUE로 전환될 때만 의미가 있어서, OR로 여러 값을 걸면 역효과. **해결**: `doesRequireRecordChangedToMeetCriteria: false`로 설정하고, 대신 중복 실행 방지 로직을 Flow 내부(Get Records + Decision)로 직접 구현한다.
- **Flow 중복 생성 방지는 Flow 내부에서 구현해야 한다**: `doesRequireRecordChangedToMeetCriteria: false`로 트리거를 넓히면 같은 레코드가 다시 저장될 때마다 Flow가 실행된다. 외부 조건이 없으면 Task/레코드가 중복 생성된다. 해결 패턴: 생성 전에 `Get Records`(같은 WhatId + Subject로 기존 레코드 조회) → `Decision`(Is Null = false이면 이미 존재 → 건너뜀) 삽입.
- **`ChangeRequestRelatedItem`에는 WorkOrder 직접 연결 필드가 없다**: Asset 필드만 있고 WorkOrder Lookup은 존재하지 않음. WorkOrder와 ChangeRequest를 연결하려면 CR의 Description/BusinessJustification에 WO ID를 포함시키거나, 별도 커스텀 필드를 만들어야 한다.

- **Profile(권한) 메타데이터는 함부로 retrieve/커밋하면 안 된다.** Profile은 조직 전체가 공유하는 파일 1개라서, 내가 고친 시점의 전체 상태를 커밋하면 다른 팀원이 이미 설정해둔 무관한 권한까지 덮어쓸 수 있다. FLS·Tab Visibility처럼 다른 트랙이 놓친 권한을 발견하면, 직접 커밋하지 말고 **해당 트랙에게 알려서 자기 PR에 포함시키게** 하는 게 맞다.

- **Approval Process의 승인자(User)는 메타데이터로 배포할 수 없다.** User는 org마다 다른 데이터(레코드)이기 때문에, 특정 이메일을 XML에 하드코딩하면 그 이메일이 없는 다른 org(CI/CD integration org 포함)에서 배포가 실패한다. **올바른 패턴: `<type>relatedUserField</type>` + `<name>Owner</name>`** — 레코드의 소유자를 승인자로 참조하도록 구조만 배포하고, 실제 승인자는 각 org에서 Setup → Approval Processes → 해당 단계 Edit으로 수동 지정한다. `<type>owner</type>`는 유효하지 않은 값(`NextOwnerType` enum에 없음)이라 에러가 남.

- **종료 상태(terminal state)는 Flow가 되돌리면 안 된다** (T3-17). `Handoff_Status__c`를 매 저장마다 재계산하는 Before Save Flow는, 이미 `ACCEPTED`(현장 인수 완료)가 된 레코드를 다른 필드 수정 때문에 다시 실행되면 `READY`로 되돌려버릴 위험이 있다. **해결: Flow 진입 초기에 "현재 값이 ACCEPTED면 아무것도 안 하고 종료" 분기를 먼저 둔다.** 자동화가 사람이 확정한 최종 상태를 덮어쓰지 못하게 하는 가드.
- **하나의 상태 전이를 Before/After 두 Flow로 나눠 구현** (T3-17): "같은 레코드의 상태 필드 갱신"은 Before Save(`TB_D1_D2_Handoff`), "그 전이에 딸린 다른 레코드 생성(Task)"은 After Save(`TB_D1_D2_Handoff_Task`)로 분리. 같은 트리거 조건을 공유하되 실행 시점이 달라 두 Flow가 된다.
- **"READY로 최초 전환될 때만" 후속 작업(Task 생성)을 실행**하려면 After Save Flow에 `doesRequireRecordChangedToMeetCriteria=true`를 건다. 이미 READY인 레코드가 다른 이유로 저장될 때마다 Task가 중복 생성되는 걸 막는다.
- **이미 있는 Validation Rule을 재사용하고 새로 만들지 않는다** (T3-17): D1→D2 게이트에서 "미승인 Baseline은 Work Order 생성 차단"은 T3-17이 새로 만든 게 아니라 기존 `Block_WO_Without_Approved_Baseline`(WorkOrder에서 연결된 Baseline의 승인 상태를 검사)이 이미 처리하고 있었다. 착수 시 완료조건을 충족하는 기존 산출물이 있는지부터 확인 → 중복 제작 방지.

- **SOQL `!=`는 NULL을 "다르다"로 쳐서 포함시킨다** (T3-19, 실측으로 잡은 버그): `Punch_Status__c != "조치완료"` 필터만 걸면, `Punch_Status__c`가 아예 없는(그 Punch 항목이 아닌 일반 레코드) 것까지 조건을 통과해버린다. 표준 SQL의 NULL 처리와 다른 SOQL만의 특징. **해결**: `Punch_Status__c` 자체를 대상으로 한 조건이 필요하면 `IsNull=false` 필터를 명시적으로 같이 걸어야 한다.
- **Roll-Up Summary는 픽리스트 필드의 "공란 아님" 필터가 신뢰할 수 없다** (T3-19, 플랫폼 한계): Roll-Up Summary 필터 조건에 `Punch_Status__c notEqual ""`(공란 아님)를 걸어도 실제로는 적용이 안 되고 공란 레코드가 계속 집계에 포함됐다(재배포 후에도 재현). Flow의 `IsNull` 연산자는 정상 동작하는 것과 대조적. **결론**: 픽리스트 필드에서 공란을 걸러야 하는 집계는 Roll-Up Summary 대신 Flow(Get Records + Loop + Update)로 만드는 게 안전하다. 필드 타입을 Summary→Number로 바꾸려면 단순 재배포로는 안 되고(`Cannot update a field from a Summary to something else`) **destructiveChanges로 필드를 삭제한 뒤 재생성**해야 한다 — 이때 Permission Set의 FLS 참조도 org에서 같이 사라지므로 필드 재생성 후 Permission Set을 한 번 더 재배포해야 한다.
- **Schedule-Triggered Flow의 Start 필터는 동적 값을 못 쓴다**: `Due_Date__c < {!$Flow.CurrentDate}`처럼 리소스를 참조하면 배포 에러("The Start element can't have a record filter condition that references a resource or element")가 난다. Start 필터가 내부적으로 SOQL WHERE절로 미리 변환되기 때문에 리터럴 값만 허용된다. **해결**: Start 필터는 리터럴 조건(`IsNull=false` 등)만 걸고, 실제 날짜 비교(`$Record.Due_Date__c < {!$Flow.CurrentDate}`)는 트리거 이후의 **Decision 요소**로 옮긴다 — Decision 안에서는 리소스 참조가 허용된다.
- **Flow formula에서 픽리스트 필드를 텍스트에 바로 이어붙이면 에러난다**: `"텍스트: " & {!$Record.픽리스트필드}`는 "Field $Record is a picklist field. Picklist fields are only supported in certain functions" 에러가 남. **해결**: `TEXT()` 함수로 감싸서 `TEXT({!$Record.픽리스트필드})`로 변환 후 연결.
- **Permission Set(fieldPermissions) XML도 Flow와 같은 "요소 그룹핑" 스키마 제약을 받는다**: `<editable>`·`<field>`·`<readable>`을 알파벳 순서(editable→field→readable)가 아니게 섞어 쓰면 "Element X is duplicated at this location" 에러가 난다. 새 `<fieldPermissions>` 블록을 손으로 추가할 땐 기존 블록의 태그 순서를 그대로 복사하는 게 안전하다.
- **Flow 최상위 요소들도 타입별 그룹핑뿐 아니라 "타입 간 순서" 자체가 고정돼 있다** (T3-21에서 처음 걸림): `decisions → formulas → interviewLabel/label/processMetadataValues/processType → recordCreates → recordLookups → recordUpdates → start → status` 순서(대체로 알파벳 순). 예를 들어 `<formulas>`를 `<decisions>`보다 앞에 쓰면 스키마 순서 위반으로 배포가 튕긴다. **확실한 방법은 매번 순서를 외우는 게 아니라, 이미 배포된 비슷한 구조의 Flow 파일 하나를 열어서 최상위 태그가 나온 순서를 그대로 베끼는 것.**
- **다른 Flow가 갱신한 필드를 트리거로 삼는 "체인 Flow" 패턴** (T3-21): WorkOrder가 인수되면 Flow A(T3-20)가 Asset의 `Service_Ready_Status__c`를 갱신하고, 그 Asset 갱신 자체가 Flow B(T3-21)의 트리거 조건이 되어 이어서 실행된다. 한 Flow에서 다 처리하지 않고 두 단계로 쪼갠 이유: 두 Flow가 관심사가 다르다(A=서비스 준비 상태 계산, B=보증·계약 생성) — 소유 Task가 달라도(T3-20/T3-21) 이런 식으로 자연스럽게 이어붙일 수 있다. 다만 이런 체인은 **중간 단계 Flow가 먼저 배포·활성화돼 있어야만 뒤 Flow가 실제로 실행된다** — 순서 의존성이 코드가 아니라 "트리거 조건"으로만 존재해서 눈에 잘 안 띈다.
- **After-Save Flow가 자기 자신(트리거 레코드)을 recordUpdates로 갱신하면 재귀 실행이 한 번 더 일어난다.** DML(진짜 UPDATE)이 발생하므로 같은 레코드에 대해 Flow가 다시 한번 시작된다 — 무한루프처럼 보이지만, 이미 값을 채워놓은 상태라 그 다음 실행에서 "이미 값 있음 → 종료" Decision 가드에 바로 걸려서 2회로 끝난다. **이 패턴(자기 갱신 + 진입 시 가드)은 "한 번만 기록하고 그 이후엔 절대 안 바뀌어야 하는 값"(보증 기산일처럼)을 구현하는 표준적인 방법**이다 — Before Save Fast Field Update로는 안 되는 이유는, 같은 트랜잭션에서 Entitlement·Service Contract 같은 "다른 레코드 생성"도 같이 해야 해서 반드시 After Save여야 하기 때문.

- **화면에서 필드가 비어있으면 "권한(FLS) 문제"부터 의심하기 쉬운데, Flow의 Entry Criteria(시작 조건) 미충족이 원인인 경우가 실제로 더 잦다** (T3-16 재검증, 2026-08-26): `WOLI_Baseline_Spec_AutoLoad` Flow는 `Line_Item_Role__c='시험'` AND `Measurement_Item_Code__c≠공란`이 둘 다 맞아야 시작된다. 테스트용으로 빈 WOLI를 만들면 이 두 필드가 비어있어 Flow 자체가 조용히 실행 안 되고, 그 결과 기준값·허용상한·허용하한·경고까지 관련 필드 전부가 비어 보인다 — 겉보기엔 "권한이 없어서 안 보이는 것"과 똑같이 보인다. **구분법**: App Builder(관리자 편집 모드)에서 필드가 이미 배치돼 있는지 먼저 확인(FLS와 무관하게 항상 보임) → 배치돼 있는데도 실제 레코드 화면에서 비면 그때 FLS 확인 → 그래도 정상인데 값 자체가 안 채워지면 **Flow Start 요소의 filters(Entry Criteria)를 git/Flow Builder에서 직접 열어서 어떤 필드가 어떤 값이어야 하는지 확인**하는 게 세 번째 단계.
- **재시딩(CSV/Data Loader)이 Screen Flow의 부수효과(자기참조 Lookup 연결)를 건너뛸 수 있다** (T3-13 재검증, 2026-08-26): `WOLI_Retest_Create` Screen Flow는 재시험 WOLI를 만들 때 `Parent_Line_Item__c`·`Root_Line_Item__c`를 자동으로 채우도록 구현돼 있는데, 일괄 시딩된 재시험 데이터엔 `Retest_Round__c`(단순 숫자)만 채워지고 자기참조 Lookup은 비어 있었다. **자기참조 Lookup은 부모 레코드의 실제 Salesforce ID를 알아야 연결 가능**해서, CSV 1차 입수만으론 못 채우고 별도 2차 업데이트(부모-자식 ID 매핑)가 필요하다 — 이 2차 단계가 시딩 스크립트에서 빠지기 쉬운 지점이라는 걸 기억해둘 것.
