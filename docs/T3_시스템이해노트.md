# T3 시스템 이해 노트

> Task를 하면서 자연스럽게 쌓이는 "왜 이렇게 만들어졌는가"에 대한 이해.
> Salesforce 어드민 노하우(T3_학습정리본.md)와 달리, 이 문서는 한 층 위 — 시스템 구조·소프트웨어 설계·플랫폼 작동 원리 — 를 다룬다.
> Task가 끝날 때마다 새로 알게 된 것이 있으면 말 안 해도 자동으로 추가된다.

---

## 1. 이 프로젝트의 기술 스택 전체 그림

```
[사용자(현장 기술자·영업·오도면)]
        ↕ 브라우저 / Salesforce 모바일 앱
[Salesforce Platform]
  ├─ 데이터 레이어:  Object(테이블) + Field(컬럼) + Record(행)
  ├─ 로직 레이어:   Flow / Validation Rule / Approval Process / Apex(코드)
  ├─ 화면 레이어:   Page Layout / Lightning App Builder / LWC(커스텀 컴포넌트)
  └─ 연동 레이어:   Platform Event / Apex Callout / External Service → ERP·PLM·BMS
        ↕ Metadata API
[개발 환경 (로컬 PC)]
  ├─ VS Code + SFDX 플러그인
  ├─ force-app/ 폴더 ← 메타데이터 XML 파일들
  └─ git → GitHub → 팀 저장소(sf-team-1to10)
        ↕ Sandbox (T3DLV)
[각 개발자의 개인 테스트 환경]
```

**핵심 원리**: Salesforce는 "설정값(메타데이터)과 실제 데이터(레코드)가 완전히 분리"된 플랫폼이다.
- **메타데이터** = 객체·필드 정의, Flow, Validation Rule 등 → XML 파일로 관리, git으로 버전 관리, deploy로 org에 반영
- **데이터(레코드)** = 실제 고객·장비·작업 정보 → org 안에만 있음, git으로 관리 안 됨, 환경마다 다름

### CLI란 무엇인가

"명령어를 글자로 쳐서 컴퓨터를 조작하는 방식." 반대말은 GUI(마우스로 버튼 클릭 — Salesforce Setup 화면 같은 것). 지금 이 프로젝트에서 쓰는 CLI 세 가지:

- `git` — 버전 관리 CLI (`git status`, `git push`, `git checkout`)
- `gh` — GitHub CLI (`gh pr create`, `gh pr list` — PR을 브라우저 클릭 없이 명령어로 조작)
- `sf` — Salesforce CLI (`sf project deploy start`, `sf sobject describe` — Setup 화면 클릭 없이 메타데이터 배포·조회)

**왜 CLI인가**: 마우스 클릭은 사람이 매번 반복해야 하지만, 명령어는 글자로 남아 **재현 가능**하다. Agentforce Vibes가 배포·조회를 대신할 수 있는 근거도 이거다 — "클릭"이 아니라 "명령어"라서 AI가 대신 실행할 수 있는 것.

### CI/CD란 무엇인가

"사람이 매번 손으로 하던 확인·배포 작업을, 코드가 특정 상태가 될 때마다 자동으로 실행되게 만든 파이프라인."

- **CI(지속적 통합)** — PR을 올리거나 push할 때마다 자동으로 "배포해도 안전한가"를 검사.
- **CD(지속적 배포)** — 그 검사를 통과하고 merge되면, 사람이 또 배포 명령을 치지 않아도 자동으로 실제 org에 반영.

**GitHub Actions**가 이걸 실행해주는 도구다. `.github/workflows/*.yml`에 "언제, 뭘 자동으로 실행할지"를 적어두면, GitHub이 그 조건에 맞을 때마다 가상 서버를 띄워 스크립트를 대신 돌려준다.

**이 저장소에 실제로 있는 것 — `.github/workflows/pr-develop-branch.yml`**:
```
on: pull_request (main 대상, force-app/** 변경 시, PR 열리거나 새 커밋 push될 때)
  → sf CLI 설치 → sfdx-git-delta로 변경분만 추출 → 코드 스캔
  → integration org에 --dry-run 배포 (RunLocalTests)
  → destructive change도 --dry-run 검증
```

**중요한 정정**: 실제 파일을 열어보면 두 배포 단계 모두 `--dry-run`이다. 즉 **이 저장소엔 CI(자동 검증)만 있고 CD(자동 실제 배포)는 없다.** PR 단계에서 "이 코드가 안전하게 배포될 수 있는가"만 자동으로 검사해줄 뿐, 실제 org 반영은 여전히 사람(또는 Agentforce Vibes)이 `deploy_metadata`를 손으로 실행해야 한다.

```
로컬에서 코드 작성 → push → PR 생성
                              ↓
              [CI · GitHub Actions] integration org에 dry-run 검증만
                              ↓ (통과)
                    T0가 PR 머지 (main에 합침)
                              ↓
              (자동 배포 없음 — 실제 org 반영은 여전히 사람/AI가 수동으로)
```

**이 프로젝트에서 실제로 걸렸던 사례**: CLAUDE.md 트러블슈팅에 있는 "Permission Set에 미merge 브랜치 필드를 포함하면 CI/CD 대상 org에서 배포 실패"가 이거다. 여기서 "CI/CD 대상 org"는 정확히는 **이 dry-run 검증이 도는 `integration` org**를 가리킨다 — 그 org엔 아직 없는 필드(다른 미merge 브랜치의 필드)를 참조해서 **자동 검증이 스스로 실행하다가 실패**한 것이지, 자동 배포가 실패한 게 아니다.

**둘의 관계**: CLI는 "어떻게 명령을 내리는가"의 방식이고, CI/CD는 "그 명령이 언제·왜 자동으로 실행되는가"의 파이프라인이다. GitHub Actions는 그 파이프라인을 실제로 돌려주는 실행 엔진이다. 서로 다른 층의 개념이라 섞어서 이해하면 안 된다.

### XML이란 무엇인가

**데이터를 태그(`<태그이름>내용</태그이름>`)로 감싸서 구조화해 표현하는 텍스트 형식.** 웹페이지를 만드는 HTML과 문법 구조 자체는 똑같은데, 목적이 다르다 — HTML은 "화면에 어떻게 보여줄지", XML은 "데이터를 어떻게 표현할지"(화면과 무관한 순수 구조). Salesforce는 필드·Flow·Permission Set 같은 **설정 정보 자체**를 이 형식으로 저장한다 — `force-app/` 안의 모든 `.xml` 파일이 "이 org에 뭘 만들어라"는 명세서다.

**여닫는 태그가 정확히 짝이 맞아야만 유효한 문서로 인정된다.** 태그 하나가 짝 없이 더 들어가면(예: `<readable>`이 중복) 그 파일을 해석하는 프로그램이 "이 구조를 어떻게 읽어야 할지" 자체를 못 정한다 — 오타 하나가 문장 하나만 이상하게 만드는 게 아니라, **파일 전체의 구조가 깨져서 통째로 파싱 실패**한다. Permission Set처럼 여러 트랙이 공유하는 큰 XML 파일에서, 손으로 줄을 추가하다 이 규칙을 어기면 그 파일을 건드리는 모든 배포가 막힌다.

### CI가 "무엇이 바뀌었는가"를 판단하는 단위 — 줄이 아니라 파일

이 저장소 CI는 `sfdx-git-delta`로 "이번 커밋에서 뭐가 바뀌었는지"를 뽑아 그 조각만 검증 org에 배포한다. 그런데 이 도구는 **XML 메타데이터 파일을 "파일 단위"로 변경 여부를 판단**한다 — git의 line-by-line diff와는 다른 층의 판단이다. `Permission Set`처럼 필드 권한 수백 줄이 한 파일에 몰려 있는 메타데이터를, 필드 하나만 추가해도 **파일 전체가 "이번에 바뀐 것"으로 묶여 배포 검증에 들어간다.**

이게 실제로 사고를 냈다: T3-20이 자기 Asset 필드 6개의 FLS만 추가했는데, 같은 Permission Set 파일 안에 **T3-18이 이미 넣어둔(그리고 아직 통합 org엔 안 배포된) 다른 필드 참조**까지 같이 검증 대상에 끌려 들어가면서, T3-20이 손도 안 댄 부분 때문에 T3-20의 CI가 막혔다(T3-19도 같은 이유로 막힘). **공유 메타데이터 파일은 "내가 고친 부분만 영향받는다"는 직관이 안 통한다** — 파일을 열면 그 파일 전체의 현재 상태(다른 트랙 몫 포함)를 책임지게 된다는 걸 뜻한다.

### FlexiPage가 Page Layout을 완전히 대체하는 이유

Lightning Record Page(FlexiPage)는 Page Layout 위에 "얹히는" 게 아니라 **통째로 대체하는 별도의 화면 정의 시스템**이다. 객체에 커스텀 FlexiPage가 org default로 지정돼 있으면, 그 순간부터 Page Layout에 뭘 추가해도 화면엔 반영되지 않는다 — 화면을 그리는 주체가 아예 바뀌었기 때문이다. 이건 Salesforce가 점진적으로 화면 시스템을 발전시켜온 역사의 흔적이다: Classic 시절엔 Page Layout이 유일한 화면 정의였고, Lightning이 오면서 더 유연한 컴포넌트 조립 방식(FlexiPage)이 추가됐는데, **둘을 동시에 쓸 수 없고 하나가 다른 하나를 완전히 이긴다.** 이 프로젝트에서 WorkOrder처럼 커스텀 FlexiPage를 쓰기 시작한 객체는, 그 뒤로 그 객체에 필드를 추가하는 모든 태스크가 "필드 배포"와 "화면 배치"라는 **두 번의 별도 작업**을 요구한다 — 하나를 빠뜨려도 배포 자체는 성공하기 때문에, 화면에서 실제로 안 보일 때까지 아무도 눈치 못 채는 구조적 함정이 된다.

## 2. 백로그가 이 순서로 짜인 이유

### 왜 Sprint 0이 "환경 준비"인가

코드를 짜기 전에 공사판 세우는 것과 같다. Salesforce에서는 Field Service 관리 패키지처럼 "설치해야만 객체가 생기는" 것들이 있고, 이게 없으면 그 위에 뭘 만들 수가 없다. T3의 거의 모든 Task가 WorkOrder에 걸려있고, WorkOrder는 Field Service 패키지가 있어야 제대로 동작하므로 가장 먼저 켜야 한다.

### 왜 Sprint 1이 "데이터 모델 → 화면" 순서인가

**데이터 모델(객체·필드)이 없으면 화면을 만들 수가 없다.** 화면은 결국 "어떤 필드를 어디에 보여줄까"인데, 그 필드가 없으면 배치할 게 없다. 그래서:
1. 먼저 객체·필드를 만들고 (T3-02~T3-09)
2. 그 다음 화면에 배치하고 (T3-10~T3-11)
3. 그 다음 로직을 추가한다 (T3-12~T3-14)

이건 소프트웨어 개발 일반 원칙과 같다: 스키마(Schema) → UI → 비즈니스 로직.

### 왜 Sprint 2가 "자동화 → AI → 포털" 순서인가

자동화(T3-15~T3-19)는 이미 만든 데이터 모델 위에서 동작하는 규칙이다. AI(T3-22)는 그 데이터가 실제로 채워진 상태에서야 의미 있는 답을 낸다. 포털(T3-23)은 데이터·로직·권한이 모두 완성된 후 외부에 공개하는 마지막 레이어다. **기반이 없으면 그 위 레이어는 공허하다.**

### 왜 T3-21에서 범위를 끊었는가 (2026-08-21 결정)

T3-22~25(Agentforce 3건 + Portal 1건)는 원래 백로그에 있었지만, **"자동화 기반이 갖춰진 뒤에야 AI·포털이 의미 있다"는 위 원칙을 실제로 적용한 결과 보류를 선택했다.** T3-21(보증 기산)까지가 필드·Flow·Validation Rule 같은 **결정적 자동화(deterministic automation)**의 마지막이고, 그 다음 층(Agentforce·Experience Cloud)은 "무엇을 자동화할지"에 대한 판단 자체가 아직 안 끝난 영역이라 재기획이 필요하다고 본 것 — 이건 "순서가 안 됐다"가 아니라 "그 위 레이어를 지금 짓는 게 아직 이르다"는 판단이다. 기반 레이어(T3-01~21)를 먼저 흔들림 없이 완성하고, AI/포털은 그 위에 무엇을 올릴지 별도로 설계하는 게 이 프로젝트가 걸어온 계층 구조(데이터→화면→로직→자동화→AI→포털)와 일관된다.

### 왜 Task 하나가 필드 몇 개 + Validation Rule 1개처럼 묶이는가

**"한 번에 배포되어야 의미가 있는 단위"로 묶인다.** T3-09를 예로 들면, Acceptance_Type__c 필드 없이 "최종인수 시 Critical Punch 차단" Rule을 배포하면 Rule이 참조할 필드가 없어서 배포 자체가 실패한다. 필드와 그 필드를 쓰는 Rule은 반드시 같이 배포되어야 한다 → 같은 Task에 묶인다.

## 3. 플랫폼이 실제로 어떻게 동작하는가

### 사용자가 저장 버튼을 누르면 일어나는 일

```
사용자가 [저장] 클릭
    → Salesforce 서버가 레코드 저장 요청 수신
    → Before Save Flow 실행 (저장 전 필드값 자동 수정 가능)
    → Validation Rule 실행 (조건 위반 시 저장 차단, 에러 메시지 표시)
    → 실제 DB에 저장
    → After Save Flow 실행 (다른 레코드 생성·수정 가능)
    → 화면에 결과 표시
```

**이게 왜 중요한가**: Flow의 Before/After Save 선택이 바로 이 순서에서 나온다. "같은 레코드 필드만 바꾸면" Before Save, "다른 레코드를 건드려야 하면" After Save.

### Validation Rule이 "조건이 참이면 차단"인 이유

직관과 반대라서 헷갈리는 부분. Validation Rule의 공식은 **"이 상태가 되면 안 된다"는 조건**을 적는다. 공식이 `TRUE`를 반환하면 → 저장 차단. 즉, "잘못된 상태"를 공식으로 표현하면 된다. T3-09의 경우: `Acceptance_Type__c = '최종인수' AND Critical_Punch_Count__c > 0` → 이 상태이면(TRUE) 저장 차단.

### 메타데이터 API vs Setup UI — 같은 결과인데 왜 구분하는가

Setup UI로 필드를 만들면 Salesforce가 내부적으로 여러 후처리를 자동으로 해준다(FLS 자동 설정, Profile에 권한 추가 등). 메타데이터 API(XML 파일 배포)는 **"정확히 파일에 적힌 것만" 반영**한다 — 후처리가 없다. 그래서 API 배포 후 FLS가 누락되는 일이 생긴다. 어느 쪽이 더 좋은 게 아니라, **반복 가능하고 버전 관리 가능한 배포를 위해 API를 쓰되, 그 트레이드오프를 알고 있어야 한다.**

### 승인 프로세스가 레코드를 "잠그는" 원리 (T3-15·T3-17에서 발견)

Approval Process는 단순히 승인자에게 알림만 보내는 게 아니라, **제출~최종응답 사이에 레코드 자체를 잠근다.** 이 잠금의 강도는 두 설정이 결정한다:

- `recordEditability` — 승인 진행 중 **누가** 편집할 수 있는가. `AdminOnly`면 관리자만, `Unlocked`면 제출자도 편집 가능.
- `finalApprovalRecordLock` — 최종 승인 **후에도** 잠긴 채로 둘 것인가. `false`면 승인 완료 시 잠금이 풀린다.

**"관리자인데도 편집이 안 된다"의 진짜 원인은 대개 세 겹**: (1) 승인 진행 중 잠금 + `AdminOnly`, (2) Lightning이 잠금 상태를 캐시해 오래 물고 있음, (3) 그 위에 FLS/레이아웃 문제가 겹친 것처럼 보임. **필드·FLS·레이아웃을 아무리 뒤져도 안 풀리면 승인 프로세스 설정부터 의심**해야 한다 — T3-17 QA에서 필드 쪽을 한참 헤맨 뒤에야 원인이 T3-15의 `AdminOnly`였음을 찾았다.

### 게이트는 하나가 아니라 "체인"으로 흐른다 (D1→D2)

Technical Baseline이 설치(D2)로 넘어가려면 **성격이 다른 관문 두 개를 순서대로** 통과해야 한다:

```
[D1: 기술 기준선 확정]
   ① 엔지니어링 승인 (Approval_Status=승인)   ← 오도면(엔지니어)이 기술적으로 확정
   ② 필수 스펙 5개 모두 채워짐               ← Product/Quantity/Delivery_Date/PLM_Revision
        → Handoff_Status__c = READY 로 자동 전환
        → 강시공에게 "인수 확인" Task 자동 배정
[D2: 현장 인수]
   ③ 강시공이 인수 확정 (Handoff_Status__c = ACCEPTED)  ← 현장이 인수
        → 이때만 설치 Work Order 생성이 열림
```

**승인(①)과 인수(③)는 별개 주체·별개 의미의 관문**이다. 엔지니어의 승인은 "기술적으로 맞다", 현장의 인수는 "받아서 설치하겠다". 둘 다 통과해야만 다음 단계가 열리도록 게이트를 겹쳐, 승인 안 된 기준선으로 설치가 시작되는 사고를 구조적으로 막는다. **한 번 ACCEPTED가 된 뒤에는 Flow가 재계산으로 상태를 되돌리지 않도록**, Flow 진입 초기에 "이미 ACCEPTED면 종료" 분기를 둔다 — 종료 상태(terminal state)는 자동화가 되돌리면 안 되는 값이기 때문이다.

### "완료 게이트가 있다"와 "모든 하위 완결성이 보장된다"는 다르다 (T3-16에서 발견)

T3-17의 D1→D2 게이트는 Baseline이 READY/ACCEPTED가 되려면 **Baseline 자신의 필드**(Product·Quantity·Delivery_Date·PLM_Revision 등)가 다 채워져야 한다고 강제한다. 그런데 `Technical_Baseline_Spec__c`(측정 항목별 기준값)는 Baseline의 **자식 레코드**이고, 이 게이트가 자식 레코드 개수·완결성까지는 검사하지 않는다. 그 결과 **Baseline이 정식으로 승인·인수돼도, Spec 항목 6개 중 하나가 빠진 채로 시운전까지 넘어갈 수 있다** — 실제로 재현해서 확인했다.

**교훈**: "이 상태가 되려면 게이트를 통과해야 한다"는 게이트가 정확히 무엇을 검사하는지 뜯어봐야 한다. 부모 레코드의 필드 완결성과 자식 레코드 집합의 완결성은 서로 다른 검사이고, 하나가 보장된다고 다른 하나까지 저절로 보장되지 않는다. T3-16의 `Spec_Load_Warning__c` 필드는 정확히 이 빈틈(다른 어떤 게이트도 안 잡아주는 빈틈)을 메우기 위해 존재한다.

### 픽리스트는 같은 개념이라도 필드마다 독립적으로 정의된다 (T3-16에서 발견)

`WorkOrderLineItem.Measurement_Item_Code__c`와 `Technical_Baseline_Spec__c.Measurement_Item_Code__c`는 이름은 같지만 **완전히 별개로 정의된 두 개의 restricted 픽리스트**다. 값 목록이 하나로 공유되는 게 아니라, 필드를 만들 때마다 각자 따로 타이핑해서 넣는다. 그래서 한쪽에 "수온", 다른 쪽에 "수은"처럼 **각자는 문제없이 restricted인데 서로 어긋나는 상태**가 조용히 만들어질 수 있다 — restricted 설정은 "이 필드 안에서 유효한 값만 허용"할 뿐, "다른 객체의 같은 이름 필드와 값이 일치"하는 건 전혀 보장하지 않는다.

두 필드가 서로를 참조해서 매칭해야 하는 관계(Flow가 WOLI의 코드로 Spec을 찾는 것 같은)라면, **값 목록이 하나라도 갈리면 그 항목은 영원히 매칭이 안 된다** — 에러도 안 나고 그냥 조용히 실패한다. Global Value Set(여러 필드가 공유하는 픽리스트 정의)을 쓰면 이런 종류의 드리프트를 원천 차단할 수 있는데, 지금은 각 필드가 독립 값 목록이라 이 위험이 항상 남아있다.

### Flow XML은 같은 요소 타입을 한 군데로 묶어야 한다

Flow 메타데이터(XML)는 `actionCalls`·`recordUpdates`·`recordLookups` 같은 요소들이 **같은 타입끼리 연속으로 나열**돼야 하는 스키마 제약이 있다. `recordUpdates`를 파일 앞쪽과 뒤쪽 두 군데에 나눠서 넣으면 "Element recordUpdates is duplicated at this location" 에러가 난다 — 이미 있는 `recordUpdates` 블록 옆에 새 것을 붙여야 한다. Flow Builder(화면)로 만들 때는 이 순서를 자동으로 맞춰주지만, XML을 직접 손으로 편집할 땐 이 제약을 사람이 지켜야 한다.

## 4. 개발자와 플랫폼 사용자 사이를 어떻게 잇는가

### 개발자(우리)가 만드는 것 vs 사용자(현장)가 보는 것

| 개발자가 만드는 것 | 현장 사용자가 경험하는 것 |
|---|---|
| WorkOrder 객체에 `Acceptance_Type__c` 필드 추가 | 인수 화면에 "인수 유형" 드롭다운이 생김 |
| Validation Rule "Critical Punch 있으면 차단" | 저장 시도 시 빨간 에러 메시지 표시 |
| Before Save Flow "측정값 → 합격/불합격 자동 판정" | 숫자 입력하는 순간 옆 칸에 자동으로 "합격" or "불합격" 표시 |
| Roll-Up Summary `Critical_Punch_Count__c` | Work Order 화면 상단에 "미해결 Critical: 2건" 숫자 항상 표시 |

**핵심 원칙**: 사용자는 시스템이 어떻게 돌아가는지 모르고, 알 필요도 없다. 개발자의 역할은 **"사용자가 잘못된 행동을 하기 어렵고, 올바른 행동이 자연스럽게 되는" 구조를 만드는 것**이다.

### 니즈를 시스템으로 번역하는 과정

```
현장 문제: "Critical 결함이 남아있는데 실수로 최종인수 해버리는 사고가 났다"
    ↓ 업무 규칙으로 번역
"Critical Punch가 1건이라도 열려있으면 최종인수 저장 불가"
    ↓ 기술 구현 결정
Validation Rule (Before Save) — 저장 자체를 차단하는 게 가장 강제력 있음
    ↓ 구현
WorkOrder.Acceptance_Type__c = '최종인수' AND Critical_Punch_Count__c > 0 → 차단
```

이 번역 과정에서 "어떤 기술 레이어를 쓸 것인가"를 결정하는 기준:
- **강제로 막아야 한다** → Validation Rule (저장 자체 차단)
- **자동으로 계산해줘야 한다** → Flow 또는 Formula
- **다른 레코드도 같이 업데이트해야 한다** → After Save Flow
- **여러 사람의 승인이 필요하다** → Approval Process
- **외부 시스템과 통신해야 한다** → Apex Callout (현재 범위 밖)

## 5. "선언형(Clicks) vs 코드(Code)" — 언제 어떤 걸 쓰는가

Salesforce의 핵심 철학 중 하나가 **"Clicks before Code"** — 코드 없이 설정으로 가능한 건 설정으로 한다.

| 방식 | 도구 | 언제 쓰는가 |
|---|---|---|
| 선언형 | Flow, Validation Rule, Approval Process, Formula | 대부분의 비즈니스 로직 — 조건 분기, 자동화, 화면 제어 |
| 코드 | Apex, LWC | 대량 데이터 처리, 외부 시스템 연동(동기 API 호출), 표준 화면으로 불가능한 UI |

**이 프로젝트에서 Apex/LWC를 아직 안 쓰는 이유**: 지금까지 나온 모든 요구사항이 Flow·Validation Rule로 커버 가능하다. "나중에 필요할 수도 있으니까" 미리 코드로 만들면, 유지보수 비용만 늘고 지금 당장 아무 이점이 없다(YAGNI: You Ain't Gonna Need It).

코드를 도입할 트리거(이 시점에 논의 시작):
1. 실제 ERP/PLM/BMS 외부 연동이 승인될 때
2. 10만 건 이상 대량 데이터 처리가 필요할 때
3. 표준 화면으로는 구현 불가능한 UI가 요구될 때

## 6. 팀 협업 구조가 이렇게 설계된 이유

### 왜 개인 Sandbox를 쓰는가

Salesforce org는 "서버 한 대"와 같다. 여러 명이 같은 org에서 동시에 작업하면 서로의 변경이 충돌하고 덮어쓴다. 각자 개인 Sandbox를 쓰면 **독립된 개발 환경**이 생겨서, 내가 실험하다 망가뜨려도 남에게 영향 없다.

### 왜 git을 쓰는가

Salesforce 자체에는 "이전 상태로 되돌리기"가 없다. git이 있어야:
- 변경 이력 추적 가능
- 잘못 배포하면 이전 버전으로 롤백 가능
- 여러 명의 변경을 PR로 검토 후 합치기 가능

### 왜 PR(Pull Request)이 필수인가

각자의 Sandbox에서 만든 것을 팀 저장소(main)에 합칠 때 **다른 사람이 검토(코드 리뷰)하는 게이트**다. T3-09에서 WorkOrder에 필드 추가했는데, 만약 T4도 같은 시점에 WorkOrder를 건드리고 있었다면 — PR 리뷰 단계에서 충돌을 발견하고 조율할 수 있다. 없으면 서로 모르고 덮어쓴다.

### merge 방향 — 두 가지를 헷갈리면 사고가 난다 (T3-17에서 확인)

git에서 "merge"라는 단어 하나가 완전히 다른 두 가지를 가리킬 수 있다. 방향이 핵심이다.

```
① feature/T3-17  →  main     (내 브랜치의 변경을 main에 합친다)
   = PR 머지. GitHub에서 T0(리뷰어)만 버튼을 누를 수 있다. 08-human-only 붉은 선.

② origin/main  →  feature/T3-17   (main에 이미 쌓인 남들의 변경을, 내 브랜치로 끌어온다)
   = 일상적인 브랜치 동기화. main은 전혀 안 건드리고, 내 브랜치 커밋만 하나 늘어난다.
     누구나(AI 포함) 해도 되는 작업 — 09-task-cycle의 "브랜치 준비"에 해당.
```

②를 "merge를 한다"고 줄여 말하면 ①(금지된 것)과 헷갈리기 쉽다. **화살표 방향이 어느 쪽인지로 구분해야 한다** — 내 것을 남의 저장소로 밀어 넣는가(①, 금지), 남의 것을 내 저장소로 끌어오는가(②, 허용).

### "stale diff"란 무엇이고 왜 생기는가

feature 브랜치가 main에서 갈라진 뒤 **한 번도 main을 다시 끌어오지 않은 채 오래 방치**되면, 그동안 main에 merge된 다른 트랙의 변경분만큼 두 브랜치가 벌어진다. 이 상태에서 PR을 올리면, GitHub이 보여주는 diff에는 **내가 실제로 만든 변경**과 **그냥 오래돼서 안 따라잡은 차이**가 뒤섞여 보인다 — 후자를 stale(오래 묵어서 생긴) diff라고 부른다. 리뷰어 입장에선 "왜 이 PR이 남의 트랙 코드를 지우려 하지?"처럼 잘못 읽힐 수 있다.

해결은 PR 올리기 전에 위 ②(`origin/main → feature/T3-17`)를 한 번 실행해 두는 것 — 그러면 두 브랜치 사이 커밋 차이가 0이 되고, PR diff엔 진짜 내 변경분만 남는다. T3-17에서 20커밋 뒤처진 상태로 방치돼 있었던 걸 발견하고 나서야 이 필요성이 드러났다.

### 워킹트리는 브랜치의 마지막 커밋보다도 낡을 수 있다 (T3-17에서 발견)

"브랜치가 오래됐다"와 "워킹트리(로컬 파일)가 오래됐다"는 서로 다른 문제다. T3-17 작업 중 `git status`에 다른 트랙 소유 Layout·Workflow 18개가 modified로 떴는데, 실제로는 **이미 이 브랜치의 마지막 커밋에 merge까지 끝나 들어있는 내용이 워킹트리에서만 사라져 있었다.** 원인은 org(Sandbox)에서 `retrieve`를 실행했는데, 그 org 자체가 최신 merge를 아직 못 받은 상태였고, retrieve 결과가 로컬 파일을 그 오래된 상태로 덮어쓴 것으로 추정된다.

**교훈**: tracked 파일이 modified로 뜨면 "무엇이 왜 바뀌었는지"를 diff로 반드시 확인해야 한다. `git diff`가 origin/main 대비가 아니라 **내 브랜치 자신의 HEAD 대비**로 뭘 지우고 있다면, 그건 거의 항상 사고다 — 의도한 변경이면 내가 그 파일을 왜 고쳤는지 설명할 수 있어야 하고, 설명이 안 되면 `git checkout -- <경로>`로 HEAD 상태로 되돌리는 게 맞다.

### PR은 "그 순간의 스냅샷"이 아니라 브랜치를 추적한다

같은 브랜치(`feature/T3-17`)에 커밋을 새로 push하면, 이미 열려 있는 PR이 있는 경우 **새 PR이 생기는 게 아니라 기존 PR에 그 커밋이 자동으로 추가**된다. PR 번호도 URL도 그대로다. GitHub은 "이 브랜치와 이 base(main)의 조합"을 하나의 PR로 취급하기 때문에, 같은 조합으로 또 만들려고 하면 **막고 기존 PR로 안내**한다 — compare 화면에 "이미 열린 PR이 있다"는 배너가 뜨고, Create 버튼을 눌러도 새로 생기지 않는다.

새 PR이 생기는 경우는 오직: 그 브랜치로 PR을 아직 한 번도 안 열었을 때 / 브랜치 이름을 바꿨을 때 / 기존 PR이 이미 merge되거나 close된 뒤 다시 push했을 때(이 경우는 새로 열어야 한다 — merge된 PR은 새 커밋을 못 받는다) 뿐이다.

### T0가 merge 버튼을 먼저 눌러도 사고가 안 나는 구조

"내가 push하기 전에 T0가 먼저 merge 해버리면?"이라는 걱정은 자연스럽지만, 두 가지 안전장치가 이미 있다.

1. **push 안 한 커밋은 애초에 merge 대상이 아니다.** GitHub PR merge는 "그 순간 origin에 push된 브랜치"만 본다. 로컬에만 있는 커밋은 T0 눈에 아예 안 보이므로 잘못 섞여 들어갈 수가 없다 — 다만 그 커밋은 이번 merge에서 빠지고, 나중에 반영하려면 새 PR이 필요해진다(바로 위 항목).
2. **conflict가 있으면 GitHub이 merge 버튼 자체를 막는다.** main이 그 사이 앞서가서 같은 파일을 건드렸다면 "This branch has conflicts that must be resolved"로 자동 잠긴다. 즉 **"모르고 이상한 내용이 섞여서 merge되는" 사고는 구조적으로 안 일어난다** — 최악의 경우도 "막혀서 다시 손봐야 한다" 정도지 main 오염은 아니다.

**교훈**: 타이밍을 걱정하기보다, **작업이 끝나는 대로 바로바로 push해 두는 습관**이 이 종류의 걱정 자체를 없앤다. push된 것만 안전하게 merge 대상이 된다는 원리를 기억하면 된다.

### "미루기로 한 권한 작업"과 "지금 매번 하는 권한 작업"은 다른 일이다

T3-02·03 시절 "Permission Set은 나중에(Production 배포 전에) 하자"고 미룬 건 **역할별 세밀한 권한 설계**(현장 기술자용 등 System Administrator가 아닌 실제 사용자 프로필을 위한 권한)였다. 반면 T3-12부터 매 태스크마다 `OT_T3_Construction_Access`를 갱신해온 건, **메타데이터 API로 배포한 필드는 FLS가 자동으로 안 붙어서 관리자 계정으로도 안 보이는 문제**를 풀기 위한 최소한의 작업용 우회 조치다. 이름이 같은 "Permission Set"이라 헷갈리기 쉽지만, 하나는 "제대로 된 접근 통제 설계"(여전히 미룬 상태)고 다른 하나는 "일단 검증이라도 되게 하는 임시 조치"(계속 하는 중)다 — **"미루기로 한 일이 슬그머니 당겨진 게 아니라, 애초에 다른 일이 같은 이름을 쓰고 있는 것**"으로 이해해야 한다.

### 공유 XML 파일의 버그는 브랜치에서 고쳐도 main에 안 반영되면 계속 재발한다

Permission Set의 `<readable>` 중복 버그를 T3-19·T3-20 브랜치에서 각각 따로 고쳤는데도, main 자체는 계속 깨진 채로 남아있었다(팀원이 2026-08-23에 별도로 재발견해서 고칠 때까지). **버그가 있는 게 아니라, "고친 게 main에 안 실려서 매번 새로 브랜치 딸 때마다 다시 나타나는" 구조적 문제였다.** 여러 사람이 같은 공유 파일을 각자 브랜치에서 고치면, 그 수정들은 서로의 존재를 모른 채 병렬로 쌓이고, **가장 먼저 merge되는 수정 하나만 실제로 문제를 없앤다** — 나머지는 "내 브랜치에선 해결됐다"는 착각만 남긴다. 공유 파일의 버그는 각자 브랜치에서 우회하는 것보다, **누군가 main을 기준으로 직접 고쳐서 빨리 merge하는 쪽이 훨씬 근본적인 해결**이라는 걸 실제로 겪었다.

### 왜 트랙을 "UC 단위"가 아니라 "객체 소유 단위"로 나눴는가

하나의 업무 흐름(예: 영업 → 계약 → 설치 → 인수)은 여러 객체를 가로질러 지나간다. UC 단위로 나누면 T1 영업 담당자도 WorkOrder를 건드려야 하고, T3 구축 담당자도 Opportunity를 건드려야 한다 → 충돌 빈발. 객체 소유 단위로 나누면 각자 자기 객체만 건드리고, 관계는 Lookup 필드로 연결만 한다 → 충돌 최소화.
