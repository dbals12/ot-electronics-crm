# T5 고도화 전체 시스템 아키텍처

> 이 문서는 T5 고도화 전체(가상 IoT·포털·Agent·실시간 응대·Slack·FSM·세일즈 연계)의 **최종 산출물 기준 문서**다. 지금까지 나온 모든 논의(백로그·구조정리·멘토 자문)를 하나로 합쳤다. 최상단에 전체 도식화, 이어서 기존/신규 구분, 사용자 접점, 시스템 구조, 데이터 흐름, 서비스→현장→영업 확장 단계별 아키텍처 순서로 정리한다.
>
> **용어 정정(2026-08-28)**: MIAW(=대화 채널)와 서비스 에이전트(=Agentforce Bot, 그 채널 위에서 응답하는 주체)는 다른 것이다. 응대는 **1차(Agent+Knowledge) → 2차(서정비가 같은 대화를 그대로 이어받음, 새 세션 아님) → 3차(Slack Case Swarming)** 구조다. 상세 근거는 `T5_통합서비스에이전트_구조정리.md` 7-1b 참고.

### 0-1. 신규 기능이 어떻게 붙었나 — 결합 지점

새 기능은 기존 체인을 바꾸지 않고, **기존 단계마다 원래 있던 빈틈에만** 끼워졌다. 데이터 모델·기존 필드·기존 Flow는 전부 그대로다.

| 기존 단계 | 원래 있던 빈틈 | 끼워진 것 |
|---|---|---|
| ① 고객 접수 | Agent 상담(T5-08)이 비동기 — 막히면 그냥 끝, 사람이 이어받는 경로 없음 | MIAW(T5-23)로 **같은 대화**를 사람이 이어받게 |
| ② 서정비 판단 | 근거(브리핑)는 있었지만 "이 고객이 누구인지" 보는 화면이 없었음 | Customer 360 컴포넌트(T5-25) |
| ③ Swarming | 초대 메커니즘(Expert Finder)은 있었지만 스킬 태그에 Asset Type 기준이 없었음 | Expert Finder 스킬태그에 Asset Type 추가(T5-24, 새 시스템 아니라 태그 설정) |
| ④ FSM | 이 고객사 이력만 보고 다른 고객사 사례는 못 봄 | 계정 경계 없는 Knowledge 검색(T5-26) |
| ④→⑤ 사이 | 현장 완료 보고가 FSM 앱 조작이나 사후 통화로만 가능 | Employee Agent Topic1 "작업 완료 보고"(T5-29) |
| ⑤ 사후 | Knowledge 축적까지는 있었지만 세일즈로 안 이어짐 | Employee Agent Topic2 "증설 제안 초안"(T5-28) |
| ⑥ Knowledge 등록 | 버튼은 있었지만 "새 사례였다"는 걸 시스템이 먼저 알려주지 않음 | 신규사례 자동감지 → 등록 제안 배너(T5-22 확장) |
| 전체(업무 외 시간) | 야간·주말 문의는 다음날까지 방치 | 별도 봇 아님 — T5-08 자체가 24시간 응답, 업무시간 인지 라우팅 로직만 추가 |

### 0-2. Agent가 시간을 줄이는 모습 — Before/After

| 접점 | Agent/자동화 없이 | Agent를 얹으면 | 줄어드는 것 |
|---|---|---|---|
| 고객 1차 응대 | 상담사가 Account·Contract·Case·Asset을 각각 열어 맥락 파악, 고객은 대화 중 대기 | 채팅창 옆에 Customer 360이 즉시 표시(2차 진입 시점) | 맥락 파악 시간 → 0에 가깝게 |
| 반복 문의 | 상담사가 매번 처음부터 설명 작성 | Knowledge Article 즉시 추천(1차), 맞으면 Case 자체가 안 생김 | 반복 문의 처리시간·인건비 |
| 전문가 인계 | 어떤 장비든 같은 창구로 들어와 담당자를 사람이 수소문 | Expert Finder가 Asset Type 스킬태그로 즉시 매칭 | "누구한테 물어봐야 하지" 탐색시간 |
| 인계 맥락 전달 | 인계받은 사람이 Case를 처음부터 다 읽음 | Slack에 핵심 요약이 바로 게시 | 인계 후 착수까지 시간 |
| 현장 완료→Case 종료 | 기술자가 앱 조작 또는 전화로 완료 보고, 서정비가 나중에 확인 | Employee Agent에게 상태 보고 → 서정비 즉시 알림+원클릭 종료(T5-29) | 완료~종결 사이 지연 |
| 업무 외 시간 | 야간·주말 문의는 익일까지 미대응 | T5-08 Agent가 24시간 그대로 응대, Critical만 사람이 다음날 확인 | 커버리지 24/7 확대(인력·별도 봇 추가 없이) |
| Knowledge 신규 등록 누락 | 새로 해결한 사례를 등록할지 사람이 스스로 기억해야 함 | Case 종결 시 "신규 사례였음" 자동 감지·제안 배너 | 등록 누락으로 인한 지식 유실 |

이 표가 곧 발표에서 "6시간51분→4시간"류 숫자로 이어지는 근거다 — 단, 멘토 지침대로 **숫자를 억지로 맞추지 않고, 이 표의 각 행이 실제로 얼마나 개선되는지를 검증해서 거꾸로 계산**한다.

## 2. 사용자 접점 — 페르소나별 화면 전체

## 4. 데이터 흐름 상세

### 4-1. 서비스 체인 (사람이 접수·처리)

```
Case(Symptom_Category__c/Impact_Level__c/Reported_Symptom__c)
  → Case_Assign_Entitlement_By_Impact(자동 보증판정)
  → Case_Dispatch_Briefing_Generate + 유사사례 검토(T5-20)
     입력: Technical Baseline, 인수이력(Change Request/Revision), Trend, Similar_Cases_Summary__c
     출력: 브리핑 텍스트 + 우선순위 제안
  → (인계 필요시) Slack 발신 Action(T5-10) — 브리핑 본문 포함
  → Swarming 채널(T5-24, Asset Type 매칭)
  → Work Order → WorkOrderLineItem(측정값·판정)
  → Problem(RCA) → 예방 WO 1+11건 + 점검기준 Rev 개정
  → Case 종결 → Knowledge Article(T5-22)
  → Contract 만료일·가동률 데이터 → 증설 제안 초안(T5-28)
```

### 4-2. IoT/Trend 체인 (장비가 스스로 만드는 신호)

```
가상 IoT 시뮬레이터 → IoT_Reading__e(Platform Event)
  → T5 IoT Reading Subscribe Flow → WorkOrderLineItem 생성(Source__c='SIMULATOR')
  → WOLI_Trend_Flag_Evaluate(T4) → Trend_Flag__c(정상/주의/이상)
  → [주의] 포털·Hall 대시보드에만 Pull로 표시(오탐지 방지)
  → [이상/Critical] Slack Alert 자동 발신(T5-10) — Case 있으면 브리핑 포함, 없으면 Case생성 딥링크
```

### 4-3. 두 체인의 교차점

`WorkOrderLineItem.Trend_Flag__c` 하나가 두 체인을 잇는다 — 서비스 체인은 이 값을 "출동 브리핑 근거"로 읽고, IoT 체인은 이 값을 "직접 계산"한다. 화면상 교차 지점은 포털 자산 카드(T5-07), Hall 대시보드(T5-09), Asset 레코드 페이지(T5-21), Slack Alert(T5-10) 네 곳뿐이다.

## 5. 확장 단계 아키텍처 — 서비스 → 현장 → 영업

### 1단계: 서비스 (Service) — 접수·1차 응대·인계

**시스템 구성**: Experience Cloud(MIAW) + Service Cloud(Case) + Agentforce(증상 상담+Knowledge) + Omni-Channel(실시간 라우팅) + Customer 360 컴포넌트

**데이터 흐름**: 고객 입력(자유 텍스트) → 구조화 필드 매핑(Symptom_Category__c 등) → Case → 보증 자동판정 → Customer 360 조회(Contract/Asset/Case 이력 통합 뷰)

**핵심 가치**: 상담사가 화면을 여러 개 열지 않고 한 곳에서 맥락 파악, 반복 문의는 Knowledge로 즉시 해결

### 2단계: 현장 (Field) — 전문가 매칭·출동·복구

**시스템 구성**: Slack(Case Swarming, Asset Type 라우팅, 완료 보고 양방향) + Field Service(WO, 모바일) + Knowledge(계정 경계 없는 검색)

**데이터 흐름**: Case → 출동 브리핑(Baseline+Trend+유사사례) → Swarming(전문가 자동 매칭) → Work Order → WorkOrderLineItem(현장 측정) → **Slack 완료 보고(T5-29) → 서정비 즉시 Case 종료** → Problem(RCA) → 예방 WO 확산

**핵심 가치**: "누구에게 물어봐야 하는지" 탐색 시간 제거, 현장에서 전사 경험(다른 고객사 사례 포함) 활용, 완료~종결 사이 지연 제거(양방향 Slack)

### 3단계: 영업 (Sales) — 지식화·재계약·증설

**시스템 구성**: Knowledge(Article 자동 축적) + Contract(만료일 추적) + Slack 세일즈 보조 Agent(T5-28)

**데이터 흐름**: Case 종결 → Knowledge Article 등록 → 이 Asset/Account의 서비스 이력·가동률·계약 만료일이 누적 → 영업 담당자가 Slack에서 Agent 호출 → 이력 기반 증설 제안 초안 자동 생성

**핵심 가치**: 서비스 이력이 별도 조사 없이 바로 다음 영업 기회의 근거가 됨 — "서비스 결과가 종료 보고서로 끝나지 않고 신뢰 근거로 전환된다"는 발표 시나리오의 핵심 메시지와 동일 선상
